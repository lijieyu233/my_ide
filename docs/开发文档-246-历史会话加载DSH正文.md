# 历史会话切过去要真的加载正文（DSH 会话回放）

用户反馈（2026-11-01）：

> 完全不对 我切到这个会话 但是他的输出没有加载到我这里

截图里点的是历史会话里那条带绿点「运行中」的 DSH 会话，面板正文停在 `terminated`，
和 DSH 界面里那条会话的内容对不上。

## 根因：历史列表有目录，但没有正文读取

上一版（文档 245）把历史列表改成以宿主 `session/list` 为准，于是 DSH 里发起的会话
**能出现在列表里**。但列表只带来元数据：

```js
// 旧代码（renderer/ai-panel.js）
if (!se && act !== 'ren' && act !== 'del') {
  curSessionId = id;
  rememberSession();
  renderHist();
  MI.toast('已切换到 DSH 会话；发送消息即可继续', 'ok');
  return;          // ← 正文一个字都没读
}
```

以及 `openSession(id)`：

```js
const se = loadSessions().find(x => x.id === id);
if (!se) { MI.toast('找不到该会话', 'err'); return; }   // ← 宿主会话永远走这里
```

本地 `localStorage` 里只有 MyIDE 自己发的对话带完整 `msgs`；在 DSH 界面里发起的会话
本地没有副本，所以「点击 → 只改了一个变量 → 面板还是空的」。这不是渲染问题，
是**从来没去读**。

## 宿主有正文接口：`session/page`

`@deepseek-ai/dsh-api-session-controller` 的 `session/page` 按 seq 从后向前翻页，
返回原始事件；README 明确「历史页可以在不激活 Agent 的情况下检查持久化」。
实测形态：

| 端点 | args | 说明 |
|---|---|---|
| `session/projections` | `{request:{sessionId}}` | 取 `asOfSeq` 作为 `throughSeq` 上界 |
| `session/page` | `{request:{address:{kind:'session',sessionId},throughSeq,maxMessages}}` | 逐页向前，`hasMore` 决定是否继续 |

两个实测坑：

1. **`throughSeq` 不能超过游标**：`session page through seq 9999 is past cursor 1452`。
   所以必须先读 `projections.asOfSeq`。
2. **页数预算不能按「条」写死**：一次工具密集的会话单页 50 条事件、整场 1500+ 条。
   最初把预算设成 500，实测只拿到 515/1453 —— 历史从中间开始，最早的用户发言丢失。

## 事件 → 消息的折叠（主进程 `foldHistory`）

宿主的事件形状（`turn/start`、`assistant/message`、`tool/call`、`tool/result`…）是原生
协议细节，不该漏到渲染层。主进程把它折成「一轮一轮」的部件，渲染层复用已有的
`_dshTimeline` 结构（历史回放与实时流同一段渲染）。

三个实测结论直接写进了实现：

1. **`turn/start` 不保证存在**。这条会话整场只有 1 个 `turn/start`（111 个 `step/start`、
   4 条 `user/message`，其中 3 条是系统注入）。只按它分组会把整场对话折成一轮，
   用户发言全挤在最前面。改为**每条真实用户发言开一轮**。
2. **系统注入也是 `user/message`**。`source.kind` 分别是 `runtime-context` /
   `skill-catalog` / `agent-instructions`，正文以 `<system-reminder>`、
   `Current runtime context.` 开头，单条就有 5KB。回放时画成用户气泡，第一屏全是
   系统提示，用户自己的问题被顶到很下面。折叠时按 `source.kind !== 'user'` 与正文特征跳过。
3. **`mcp__myide__*` 是面板与宿主的消息通道**，实时流里就不显示，历史也别显示。

工具结果正文按 4000 字符截断：真实会话里见过单条 40KB 的输出，不截会把历史撑爆。

## 身份：正文能看，但「继续聊」这一步没打通

只把 `curSessionId` 改掉是不够的 —— `ai-dsh.js` 的 `attach()` 仍按 `saved[key]`
（本地那条 `myide-*` 会话）派发 prompt。所以补了：

1. `ai:dsh-bind` → `bindSession()`：把当前项目的对话身份改写成目标 `sessionId`，
   同时清掉连接级 `sessions` 里的旧 attach 状态。
2. `session/resume` 的 `existing` 分支：只接手**宿主目录里确实存在**的 id
   （`NativeRpc.existing` 由 `session/list` 填充），拼错的 id 不会被 `create` 成幽灵会话。
3. 原来的 `session/resume` 校验写死 `^myide-[a-f0-9-]{36}$`，会把 `session-*` 等
   宿主既有会话直接挡死。现在只做字符集校验，存在性交给第 2 条。

### 实测边界：宿主里发起的会话能读不能续聊

`dsh-native-plugin.cjs` 里连接器把准入写死成 `^myide-[a-f0-9-]{36}$`，实测：

```
session-* => 只允许绑定 MyIDE 创建的原生会话
myide-*   => 通过（存在性在更后面校验）
```

也就是说：**正文回放对所有会话都成立；但「切到 DSH 里发起的会话后继续发消息」
会被连接器拒绝**（宿主那边不会有 MyIDE 的工具权限，硬绑定也不该做）。

#### 踩坑：绑定接口一度在撒谎

`bindSession` 最初只写映射就返回 `{ok:true}`，界面据此显示
「已载入 DSH 会话，可直接继续对话」—— 而实测真发消息会失败：

```
chat 结果 {"ok":false,"error":"只允许绑定 MyIDE 创建的原生会话"}
续聊后历史事件数 19（未增长）
```

修正：`bindSession` 先发一次**真实的 attach 探测**，把 `canContinue` 如实带回；
渲染层据此显示「已载入正文（只读）……要续聊请在 DSH 里发」，
MyIDE 自己创建的会话仍是「可直接继续对话」（实测 2 条 `myide-*` 均 `canContinue:true`）。

这里还踩了第二层坑：探测最初用 `raw()` 发**扁平 body**，而连接器的 attach 路由
第一步就校验 `client-request` 信封，于是永远回「MyIDE 连接请求无效」——
判定逻辑把它当作「不是准入拒绝」，结果又是假通过。改为 `NativeRpc.probe()`
按信封发送后才测出真实结论（`tests/dsh-native.test.js` 已锁住信封形态）。

## 已知边界

- 历史正文是**只读回放**：工具结果是静态文本，不能再点开重跑；正在运行的会话
  读到的是「当前已落盘的日志」，后续增量仍由实时流负责（切回去后继续接收）。
- **宿主里发起的会话（`session-*`）能读不能续聊**：连接器准入写死 `myide-*`，
  实测拒绝（见上一节）。MyIDE 自己创建的历史会话不受影响，正常续聊。
- 超长会话按条数与页数双重预算截断（60 页 / 5000 条事件），`truncated:true` 时
  最早的部分可能看不到；现有会话实测都在预算内（最大 1453 条）。
- 图片/附件在历史里只显示占位文本，原图不重新拉取（附件正文未进 `session/page`
  的文本块）。
- 回放时跳过系统注入的 `user/message`（`source.kind` 非 `user`，如
  `runtime-context` / `skill-catalog` / `agent-instructions`），把系统提示画成用户
  发言会让第一屏全是规则文本。
