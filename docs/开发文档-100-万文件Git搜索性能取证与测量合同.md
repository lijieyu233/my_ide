# 开发文档-100 —— 万文件 Git/搜索性能取证与测量合同

> 第十一轮持续审查，2026-10-01；产品基线 `2ec9a406a8f3f0fb51f9331699f67853254451c6`。对应 PERF-01 / SEARCH-01 / GIT-01 / QUALITY-01。
> 本轮只提交方案。R 是真实临时文件与原服务/handler 的观察，C 是源码合同，H 是未执行的完整应用或其他场景。没有修改产品、基准脚本或测试，没有关闭性能问题。

## 1. 结论与现有能力

默认 Git worker 在本轮万文件夹具上的三次扫描均低于大纲 1 秒目标；已有 stat 快捷判断、忽略目录剪枝、HEAD 缓存与 worker 隔离值得保留。不能据此宣称所有万文件项目达标：直接执行的生产 Node 路径首次超过 1 秒，legacy 路径两次超过 1 秒，index v4 回落仍明确报错。后者与 [094](./开发文档-094-Git状态与块级操作一致性取证.md) 的正确性合同一致，不能用错误空集合计作快速成功。

搜索异步让出线程并不等于扫描成本低。无命中/稀少命中要读取整个候选集合，生产 Electron 中约 2.9–3.3 秒；密集命中约 5 毫秒达到 200 条并提前返回，是不同工作量。三个并发全量搜索共读取 29997 个文件；现有后端没有取消入口。方案先补测量、合并和取消，再决定引入原生后端、增量索引或缓存。冷启动、全部进程内存、10MB 打开与真实输入延迟仍为 H。

## 3. 可复现测量条件与证明范围

### 3.1 环境与夹具

- Windows 10 专业版 10.0.19045，x64，i5-12400F，系统报告内存 25603723264 字节；Node 22.20.0、Git 2.53.0.windows.1、isomorphic-git 1.41.4、rg 15.1.0。
- 生产运行时：Electron 33.4.11 / Node 20.18.3 / Chromium 130.0.6723.191。独立 Electron 主进程中 `app.whenReady()` 后调用原服务，不创建窗口，不加载 MyIDE 主入口/renderer，也不做真实 IPC 或模拟输入。
- `%TEMP%` 的唯一 `myide-audit100-*` 目录在 C:，不是用户项目所在 D:。磁盘型号、杀软策略/后台负载未控制；不能直接外推到所有机器或实际项目。两个运行时顺序执行，没有在两轮之间清 OS 文件缓存。
- 原生 Git 构造提交：9999 个 UTF-8/LF 文本加一份已跟踪 `.gitignore`，**总已跟踪文件恰为10000**。正文路径 `src/d000/f00000.txt` 至 `src/d099/f09998.txt`，每目录最多100份；每份16行 `line alpha beta 0123456789\n`，第9000号再加 `rare_token_100\n`。初始正文总4319583字节，前500份追加 `changed\n` 后4323583字节。
- 夹具仓库独立身份、空全局 config、关闭 autocrlf/filemode/fsmonitor/untrackedCache、隔离 hooks、禁止签名；index v2。构造/提交不计入扫描耗时；构造后等待1100ms。没有联网、运行用户 hooks 或改真实仓库配置。
- 扩展场景另加100个未跟踪文件及被 `.gitignore` 忽略的5000个 `node_modules` 文件；然后仅把临时 index 改为v4。最终恢复v2并删扩展目录，才执行生产 Electron 的基线对拍。

### 3.2 调用与统计

`G.status()` 使用原 `git-service.js`，worker 使用原 `git-worker.js` 的 `{id,op:'status',args:[repo]}`。worker 首次计时包含 online 之后剩余的模块加载；没有包含创建前的完整启动时间。每组串行三次，保留原始向量与中位数；legacy/v4仅两次，逐次报告。**不估算p95，不把二次叫冷启动，不合并不同运行时的样本。**

搜索从 `main.js` 精确取出 `fs:listAll` 至 `fs:readDir` 前的两个完整注册 handler，在 VM 中绑定真实 `fs.promises`、path 和事件循环。文件桥增加薄层操作/字节计数，每次调用有少量计数开销；不是独立重写的搜索算法。计时包含整次 handler 返回，但不含 IPC、DOM 渲染、QuickOpen 排序、GitPanel 的 opState/conflicts/aheadBehind 等后续操作。

每次服务调用旁运行5ms interval，记录实际两次回调之间的最大间隔，并在完成后再等15ms收集被延后的回调。Windows 的时钟粒度会影响数值；它只是调用线程调度观察，**不是键盘响应、帧率或renderer卡顿实测**。native Git/rg 在取证宿主中用同步 CLI 方便收集结果，其宿主阻塞没有写成产品实现；未来后端必须异步 spawn。

取证首次把 Windows 的 `G.changed.file` 反斜杠直接和原生 Git 的正斜杠相比，触发夹具断言；规范化后重新测后续组。v4 的服务错误起初被夹具“成功结果”断言打断，随后改为记录错误并重测。表中后续数据来自完整成功收尾那轮；两次夹具失败不能算新增产品故障。初始 Node 基线组保留，未在失败重跑中混入新增文件。

## 5. 现有基准的合同缺口 C

`scripts/bench.js` 注释对照“1万”，循环却只有4×1250=5000；二次调用没有清进程/HEAD/OS缓存。仅计总耗时/changed数量，超1秒仍退出0，分目录commit结果未逐次断言，失败出口没有finally清临时目录。它不能证明大纲万文件门槛，更不能证明冷启动/全进程内存。本轮不改它，下一包把量测程序本身做成可重复的交付。

`App.refreshGit()`已有500ms防抖、`GitPanel.refreshSeq`已有旧status结果丢弃，不能说“完全没有防抖/迟到保护”。但 `gitCall` 逐次postMessage，worker没有同root的进行中status合并；UI丢弃过期结果也没有取消其扫描。opState/conflicts等后续await还有各自归属合同，性能包复用094/PROJECT-01，不独立创造另一套代次。

`fs:grep`已有每文件setImmediate、200结果、1MiB文件与10秒检查；逐文件stat/read，后端没有requestId/取消对象，返回只含results/truncated/elapsed。超时是否全库搜完不能由truncated=false判断（091已取证），大文件/编码/隐藏/忽略政策也不能在优化中继续静默改变。

**验收**：故意只建5000份、制造commit失败、v4不可用、漏改动、过预算均能区分并失败；连续两轮重建可复现且无临时遗留。基准失败不会触碰用户profile或现有项目。

### 100-B：Git刷新成本与服务降级（GIT-01/PERF-01）

1. root/generation负责归属，同一root最多一份status进行中；相同版本订阅者共享结果，运行期间出现保存/外部Git变化只标dirty并补一次最新扫描。切项目旧请求仍结算但不提交UI；主进程pending表有超时/error/exit收口。不能吞掉写操作之后必要的补扫。
2. 各root的写操作按094串行/版本校验，status合并只面向可共享读；不要把所有Git操作一律塞进一个不区分仓库的大锁。保留现有防抖与选择/提交信息状态。
3. worker退出尝试受控重建并暴露服务状态。不能在大库降级时静默直接执行同步扫描阻塞主进程；备选为异步原生Git或独立替代worker，均需能力探测及正确性对拍。缺Git且JS格式不支持要明确“状态不可用”，不渲染为空变更成功。
4. 若评估原生status，异步spawn+参数数组、NUL路径解析、取消/输出预算，使用`--no-optional-locks`；补tracked来源并计入端到端成本。属性/filter/autocrlf/worktree/submodule及暂存双区沿094验收；本轮原生191ms只含changed，不能直接替换还返回tracked的现服务。

**验收**：同版本burst共享扫描，期间真实修改至少一次补扫；两个root不串结果；worker error/exit/超时所有pending落定。复跑本轮500/10000、600路径、v4及094场景，默认路径不退回主线程长扫描。原生候选未满足语义时保留已有fast，而非为计时删校验。

### 100-C：可取消、可增量的搜索后端（SEARCH-01/PERF-01）

1. 在091的requestId/root/generation/定位正确性合同上加AbortSignal。新查询/关闭/切项目停止旧IO或子进程；每次readdir/read前和结果发布前检查取消。结果返回doneReason（complete/resultLimit/timeLimit/cancelled/error）、scanned/skipped/bytes，保持200是预算而非全库已搜完。
2. 用本轮fixture先比较有界并发JS（控制并发和内存，建议先从4/8两档试）与异步rg（流式JSON、输出背压/总字节限制/可终止）。低成本目录清单可复用，正文不无限缓存；文件版本/编码/忽略规则变化必须失效。直接增加10000个并行read的方案不接受。
3. 固定搜索政策：默认隐藏/node_modules、Git忽略是否启用、大小/二进制/GBK与UTF-16、字面匹配的Unicode大小写。通过同一协议给JS/rg消费；rg不支持或未安装时有明示回落，缺组件不能悄悄“无结果”。不拿`--sort path`当免费并行顺序保证，显示排序与取消/结果上限需共同定义。
4. 候选目标为该固定主机/fixture完整无命中与稀少命中<1秒、取消响应<100ms、旧请求在取消确认后不发布结果；这是待验证提案，不是大纲既有搜索指标。同时采总读取/峰值内存/首条/完成时延，JS与rg均通过091正确定位和截断合同才考虑切换。

**验收**：输入A后输入B、关闭和切项目，旧扫描不继续完整读取9999份；准确处理取消前已在途的少量IO，报告其数量。三路负载不因无限并发吞内存；0/1/200与编码/忽略/大小限制各自对拍。QuickOpen先测排序/渲染，再决定索引/虚拟化，不能因内容搜索慢就重做枚举。
