# 远程服务器概览：从「只读面板」到「可视化运维台」开发方案

> 状态：方案待评审　|　编写日期：2026-10-28　|　范围：单机运维（Docker + systemd + 进程 + 磁盘）

## 一、现状与问题

当前「概览」页（`renderer/remote-panel.js` 第 500 行起）只做了一件事：**用一条固定的只读 SSH 脚本采集数据，画成八张卡片**。采集脚本在 `src/main/remote/remote-service.js` 的 `OVERVIEW_SCRIPT`，解析在 `parseOverview`。

面板上的每一行虽然「可点」，但所有点击最终都收敛到同一个动作 —— **往已有终端里投递一条命令**。代码注释写得很明确：

```
交互：点每一行都能做进一步操作（跳文件、开终端、看日志），
全部通过「在已有终端里投递命令」实现 —— 复用现成终端。
```

这带来四个结构性问题：

| 问题 | 具体表现 |
| --- | --- |
| **不是操作，只是转发** | 点容器只是 `docker logs xxx` 打到终端，用户还得自己去敲 `restart`；点服务只是 `systemctl status` |
| **无状态、无反馈** | 面板不知道操作是否成功，刷新后才看到结果；失败也没有明确提示 |
| **看与做割裂** | 左边看指标，右边去终端操作；眼睛和手在两个地方 |
| **不可批量** | 11 个容器要重启，只能一个一个进终端敲 |

用户原话：**「当前这个功能远远不够，操作竟然只是跳到终端发个命令」**。

## 二、目标与非目标

### 目标

把概览从「监控看板」升级为「运维台」：**看到即能操作，操作有确认、有结果、有回执**。

1. Docker：容器列表 / 启停 / 重启 / 暂停 / 删除（非运行中）、实时日志（面板内）、状态与健康度
2. systemd：服务列表 / 启停 / 重启 / 重载 / 状态详情 / journal 日志（面板内）
3. 进程：按 CPU/内存排序的进程表、单进程详情、结束进程（含守护归属提示）
4. 磁盘：占用排行、大文件定位、安全清理（apt 缓存 / journal / docker 悬空镜像）

### 非目标（明确不做，避免范围失控）

- 不做多机批量管理（本次只针对当前连接的服务器）
- 不做防火墙 / 定时任务 / 用户权限 / nginx 站点配置
- 不替换现有终端与文件页；终端仍然是「要敲任意命令」的出口
- 不做实时流式监控（保持现有轮询刷新，避免长期占用 SSH 通道）

## 三、核心设计决策

### 决策 1：新增「结构化执行通道」，不再投递终端命令

**为什么不能继续投递终端**：终端是一条交互式 PTY，输出是人类可读文本、混着提示符和颜色转义，无法可靠判断「命令是否成功」。而且它占用用户正在用的终端，操作会打断用户手头的事。

**做法**：新增主进程侧 `remote.exec(id, spec)` —— 一次性执行、捕获退出码、限长输出、带超时。所有运维操作都返回结构化结果：

```js
{ ok: true, code: 0, stdout: '...', stderr: '', durationMs: 812 }
```

成功判定一律以**退出码**为准，不以文本匹配为准。

**安全约束（必须同时满足）**：

- 不接受任意字符串命令。操作由**白名单动作**组成，如 `docker.restart` + 参数 `{ name }`，在服务端拼装
- 所有参数必须经过校验：容器名/服务名匹配 `^[a-zA-Z0-9][a-zA-Z0-9_.-]{0,127}$`；不允许 `;` `|` `&` `$` 反引号 换行
- 拼装时对参数做单引号转义，杜绝注入
- 一次性执行不分配 PTY；超时默认 20 秒（日志类 30 秒）；输出上限 512KB，超出截断并标注

### 决策 2：全部操作二次确认（用户已明确选择）

**所有**写操作都弹确认，不做「安全操作免确认」的例外。为降低打扰，确认框要**信息充分**而不是简单问「确定吗」：

```
重启容器 smart-gallery-api？

影响：服务中断约 3–10 秒，正在处理的请求会失败
当前：Up 7 days (healthy)　镜像：registry/smart-gallery-api:1.4.2

[取消]  [重启]
```

只读操作（刷新、看日志、看详情、改筛选/排序）**不弹确认**。

### 决策 3：操作结果必须可核对

每个写操作结束后：

1. 显示命令退出码与 stderr（失败时）
2. **主动回读一次状态**（如重启后重新查该容器状态），而不是只报「命令成功」
3. 状态未达预期时明确说「命令成功但状态未确认」——这与项目里既有的「受理 ≠ 完成」原则一致

### 决策 4：日志查看走「面板内抽屉」，不占终端

点容器/服务的「日志」在右侧滑出抽屉，显示最近 N 行（默认 200），支持：

- 跟随开关（默认关闭；开启后按间隔拉增量）
- 关键字过滤（前端过滤，不重复请求）
- 一键复制、一键在终端打开（保留逃生口，用于交互式场景）

**不实现**真正的流式 `docker logs -f` 单连接持续推送 —— 它会长期占用 SSH 通道且断线恢复复杂。用「按需轮询增量」替代，行为可预期。

## 四、界面结构

概览页改为三段式，仍是一屏内完成：

```
┌─ 顶部：主机摘要（保持现状：发行版/内核/负载/运行时长/网速）──────────┐
├─ 左侧主区（按当前选中分类切换）───────────────────────────────────┤
│  [Docker 11] [服务 31] [进程] [磁盘]     ← 分段控件               │
│                                                                    │
│  ● smart-gallery-api    Up 7d (healthy)   CPU 2%  MEM 118MB       │
│    [日志] [重启] [停止] [详情]        ← 行内操作，点击即时生效      │
│  ● pricea-price-monitor  Up 17h (healthy)  …                       │
├─ 右侧列：告警与快捷入口（保持现状卡片，但可点进对应分类）───────────┤
└────────────────────────────────────────────────────────────────────┘
```

要点：

- **行内操作按钮**直接在列表里，不跳转、不切页
- 危险动作（停止/删除/结束进程）用红色描边区分
- 每行右侧显示该对象的关键指标（CPU/内存/端口），不用点进去才知道
- 空态与错误态都要有明确文案，不留白屏

## 五、动作清单（白名单）

### Docker

| 动作 | 命令 | 参数 | 确认 |
| --- | --- | --- | --- |
| 列表 | `docker ps -a --format ...` | — | 否 |
| 详情 | `docker inspect <name>` | name | 否 |
| 日志 | `docker logs --tail 200 <name>` | name, tail | 否 |
| 启动 | `docker start <name>` | name | **是** |
| 停止 | `docker stop <name>` | name | **是** |
| 重启 | `docker restart <name>` | name | **是** |
| 暂停/恢复 | `docker pause/unpause <name>` | name | **是** |
| 删除 | `docker rm <name>` | name（仅非运行中） | **是**（红） |
| 清理悬空 | `docker image prune -f` | — | **是**（红） |

### systemd

| 动作 | 命令 | 参数 | 确认 |
| --- | --- | --- | --- |
| 列表 | `systemctl list-units --type=service --state=running` | — | 否 |
| 详情 | `systemctl status <svc> --no-pager` | svc | 否 |
| 日志 | `journalctl -u <svc> -n 200 --no-pager` | svc, tail | 否 |
| 启动/停止/重启 | `systemctl start/stop/restart <svc>` | svc | **是** |
| 重载配置 | `systemctl reload <svc>` | svc | **是** |

> 需要 sudo 的服务：**只读操作照常**；写操作若因无权限失败，明确提示「需要 sudo 权限」，不尝试提权、不保存密码。

### 进程

| 动作 | 命令 | 参数 | 确认 |
| --- | --- | --- | --- |
| 列表 | `ps -eo pid,ppid,pcpu,pmem,rss,etime,comm --sort=-pcpu` | — | 否 |
| 详情 | 读 `/proc/<pid>/{status,cmdline}` | pid | 否 |
| 结束 | `kill -TERM <pid>` | pid | **是**（红，二次说明） |

**结束进程的额外保护**：先查该 pid 是否属于某个 systemd 服务（`systemctl status <pid>` 或 `/proc/<pid>/cgroup`）。若是，提示「该进程由 X.service 管理，杀掉会被自动拉起，建议用服务停止」，并给「改用停止服务」按钮。这是防止用户误杀托管进程的关键一步。

### 磁盘

| 动作 | 命令 | 参数 | 确认 |
| --- | --- | --- | --- |
| 占用排行 | `du -xhd1 <path>` | path | 否 |
| 大文件 | `find <path> -xdev -type f -size +100M` | path, size | 否 |
| 清理 apt 缓存 | `apt-get clean` | — | **是**（显示可释放空间） |
| 清理 journal | `journalctl --vacuum-size=200M` | size | **是** |
| Docker 悬空镜像 | 同 Docker 清理 | — | **是** |

清理类操作执行前**必须展示预计释放空间**，让用户知道自己在删什么。

## 六、实现分层

```
renderer/remote-panel.js
  ├─ 分类切换与列表渲染（Docker / 服务 / 进程 / 磁盘）
  ├─ 行内操作 → 确认弹窗 → 调 IPC → 展示结果 → 回读刷新
  └─ 日志抽屉（增量轮询、过滤、复制）

preload.js
  └─ remote.ops(action, args)          ← 单一入口，白名单在服务端

src/main/remote/remote-ops.js（新增）
  ├─ ACTIONS：动作表（命令模板 + 参数校验 + 是否危险 + 超时）
  ├─ validate(action, args)：参数白名单与转义
  ├─ run(sessionId, action, args)：执行、限长、超时、结构化返回
  └─ reread(action, args)：操作后的状态回读

src/main/remote/remote-service.js
  └─ execOnce(id, command)：一次性执行（无 PTY、带退出码）
```

**为什么新增 `remote-ops.js` 而不是塞进 `remote-service.js`**：`remote-service.js` 已经 528 行，负责连接/会话/传输/终端，职责够重。动作表与参数校验是独立主题，分开后便于单独测试与审计（安全相关的代码应该能一眼看全）。

## 七、安全设计（重点）

1. **不存密码、不提权**：需要 sudo 的操作失败即报错，不尝试 `echo pass | sudo -S`，不写 sudoers
2. **参数白名单**：所有名称类参数用正则约束，拒绝一切 shell 元字符；拼接时单引号转义并处理嵌入单引号
3. **动作白名单**：IPC 只接受枚举内的 action，未知动作直接拒绝
4. **全部二次确认**：确认框展示对象、影响、当前状态
5. **限流**：同一服务器的写操作串行执行（队列），避免连点导致状态错乱；每类操作最小间隔 500ms
6. **输出限长**：512KB 上限，防止 `docker logs` 把内存打满
7. **不记录敏感内容**：日志与命令输出不写入 `remote.json`；操作审计只记录动作名、参数、退出码、时间

## 八、分阶段交付

### 阶段一：执行通道 + Docker 全操作（核心）

- 新增 `execOnce` 与 `remote-ops.js`（动作表、校验、执行、回读）
- Docker 分类：列表、启停、重启、日志抽屉、详情、删除
- 全部操作二次确认 + 结果回执 + 状态回读
- 验收：真实 SSH 夹具上完成「重启容器并确认状态变化」

### 阶段二：systemd + 日志

- 服务列表、启停、重启、重载、状态详情、journal 抽屉
- 无 sudo 权限的失败路径明确提示
- 验收：停止一个测试服务并确认状态；权限不足时给出可读错误

### 阶段三：进程 + 磁盘

- 进程表（可排序）、详情、结束进程（含 systemd 归属保护）
- 磁盘占用、大文件、三种清理（带预计释放空间）
- 验收：托管进程被拦截并引导到服务停止；清理项显示释放空间且执行后核对

## 九、验证方式

沿用项目既有做法，不自造「假通过」：

- **服务层单元测试**（`tests/remote-ops.test.js`）：参数校验拒绝注入、动作白名单拒绝未知动作、输出截断、超时
- **集成测试**（`npm run test:remote` 扩展）：回环地址真实 SSH 夹具，跑 Docker 动作（用 `docker` 可用时跳过，不可用则用桩脚本）
- **端到端自检**（`npm run check:remote` 扩展）：隐藏 Electron 实例，通过真实 preload/IPC 点「重启」，核对最终状态与 UI 回执
- **人工验收**：在你的腾讯云服务器上实际操作一次重启容器与清理 journal

> 上一轮的经验：改全局行为必须同时验证**不触发**的一侧。本次对应要求是 —— 每个「操作生效」的用例，都要有「只读操作不弹确认」与「未连接时不报错崩」的对照用例。

## 十、风险与对策

| 风险 | 对策 |
| --- | --- |
| sudo 权限不足导致大量操作不可用 | 只读照常；写操作明确报「需要 sudo」，不假装成功 |
| 用户误杀关键进程/停掉关键服务 | 全部确认 + systemd 归属检测 + 危险动作红色 + 二次说明影响 |
| 轮询刷新与操作并发导致状态错乱 | 写操作串行队列；操作后强制回读一次 |
| SSH 通道被长任务占用 | 一次性执行 + 超时；日志用增量轮询而非长连接 |
| 命令注入 | 动作白名单 + 参数正则 + 单引号转义 + 拒绝元字符 |

## 十一、待确认

1. 是否需要**审计日志**（记录谁在什么时候重启了什么）？当前方案只存内存，不落盘。
2. Docker 操作是否需要支持**非运行中容器的启动**（当前列表含 `-a`，会看到已停止容器）？
3. 磁盘清理的**默认路径**用 `/` 还是当前主目录？`du -x` 全盘在 40GB 机器上约需数秒，可接受。
