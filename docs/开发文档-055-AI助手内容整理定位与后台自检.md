# 开发文档-055 · AI 助手改为「内容整理」定位 + 自检后台化

日期：2026-09-21
涉及：`renderer/ai-panel.js`、`renderer/index.html`、`renderer/styles.css`、`main.js`、`scripts/check-ui-steps.js`

---

## 一、背景与一次误判

用户诉求：**「当前的 AI 助手体验很糟糕。我并不是要一个能写代码的强大 agent，只是想做一个内容整理的工具，比如帮我修改文档、从当前项目查询内容。」**

我第一次的调研结论是错的，必须记下来：

> 我列了一张「能力缺口」表，把「只能整文件读」「没有 read_section」「write_file 只能覆盖」「list_files 无类型过滤」全标成 ❌。

用户一句话点破：**「能做一个 AI 编程工具，那必然能满足我的需求。」**

复盘：那五条里**真正"做不到"的是零条**。

| 我标的 | 真相 |
|---|---|
| 只能整文件读 | `read_file` 能读任何文本文件，只是费 token —— **成本问题，不是能力问题** |
| 没有 read_section | 模型读完自己定位，或 `search_files` 找行号再读，本来就能做 |
| write_file 只能覆盖 | 传一个新路径就是"另存"，本来就能做 |
| list_files 无过滤 | 列出来自己筛，十几个文件的目录毫无压力 |

而「改文档」的本质就是 **读文本 → 定位片段 → 替换片段 / 覆写**，正好是现有 5 个工具的定义。

**教训：不要把"效率优化"包装成"能力缺陷"。** 那种表格会误导决策 —— 用户差点就去补一堆根本不需要的工具。判断标准应该是「这件事在现有原语下**不可达**吗」，而不是「有没有现成的专用函数」。

因此本次改动**不新增任何工具**，只动两处：**提示词定位** + **UI 呈现**。

## 二、改动一：提示词从「编程助手」改为「通用助手（内容整理优先）」

`renderer/ai-panel.js` 的 `AGENT_SYS`：

```diff
- '你是 My IDE 内置的 AI 编程助手，可以调用工具查看和修改用户的项目文件。'
+ '你是 My IDE 内置的 AI 助手，可以调用工具查看和修改用户项目里的文件。'
+ '用户主要拿你整理内容（改文档、查资料、归纳改写），也会让你处理代码，两者用同一套规则。'
```

规则同步调整，把「省 token」和「说人话」写进去（这是内容整理场景的真实痛点）：

```diff
  1. 动手前先看真实内容（list_files / search_files / read_file），不要凭空猜测
  2. 改文件优先用 replace_edit，只改要动的那一段；只有新建文件或整篇重写才用 write_file
  3. replace_edit 的 search 必须与文件内容逐字符一致（含缩进、空行），不确定就先 read_file
+ 4. 文件很长时不要整篇读：先用 search_files 定位到相关段落，再按需读取 —— 省时间也省额度
  5. 需要多步操作就分多轮调用，每轮等工具结果回来再决定下一步
- 6. 需要运行验证（跑测试/启动脚本）时用 run_command，一条命令只做一件事
+ 6. 只在确有必要时用 run_command（跑测试 / 验证），一条命令只做一件事
  7. 全部任务完成后用中文说明改了什么，不再调用工具
+
+ ## 表达
+ 说人话：结论先行、少堆术语，不要输出与用户要求无关的技术细节。
```

**关键决定：保留 `run_command`、保留全部 5 个工具、不加「助手定位」开关。**
编程能力是超集，砍掉只会让工具变弱；要解决的是「模型把整理文档理解成工程任务」，那是提示词问题，不是工具集问题。

## 三、改动二：AI 面板 UI 四处修正

对着用户截图逐处对应：

| # | 问题 | 改法 |
|---|---|---|
| 1 | 顶栏 4 个按钮是字符符号 `⟲ ✚ ⚙ ✕`、标题是 `🤖` emoji，与刚统一成 SVG 的提交/大纲面板不一致 | 标题改 SVG 星形图标 + 文字；4 个按钮全换 `svg.ic`（撤销/新建/设置/关闭） |
| 2 | **空状态没有任何「能做什么」的入口** —— 42px 大 emoji + 三行灰字飘在虚空，这是「体验糟糕」的直接来源 | 改卡片（与启动页同一套视觉语言）+ **4 个场景快捷入口** |
| 3 | 底部 `📎 附当前文件`（中文按钮很宽）与输入框挤一行，输入框被压 | 附件改**纯回形针图标**（38×38 方形，title 保留说明）；实测输入框占栏宽 291/399 ≈ 73% |
| 4 | placeholder 英文 `Ask anything…` 混中文括号 | 改「描述你想怎么整理…（Enter 发送 / Shift+Enter 换行 / @ 引用文件）」 |

场景入口（`QUICK_PROMPTS`）不是摆设，点了会做两件事：

```js
{ label: '整理当前文档', file: true, text: '把当前打开的文档整理一下：理顺结构、统一格式，改完先给我看 diff' }
{ label: '提取要点',     file: true, text: '读一下当前文档，按章节提取要点，用简洁的列表整理给我' }
{ label: '按标题重组',   file: true, text: '按标题层级重新组织当前文档的内容，保持原意不变，改完给我看 diff' }
{ label: '在项目中查找', file: false, text: '在项目里查找：' }
```

1. 把指令填进输入框并聚焦（用户不用自己想怎么问）；
2. **整理类指令自动把当前打开的文件挂为上下文** —— 否则模型还得自己猜"当前文档"是哪个。没打开文件时给提示而不是静默失败。

未配置模型时仍然只说「去配置」，不给场景入口（避免点了必然失败的按钮）。

顺带把 AI 面板内部的 px 字号统一改成 em（9 处：`#ai-model` / `.ai-usage` / `.ai-ctx-chip` / `.ai-at-*` / `.ai-copy` / `.ai-tool`），跟上上一轮「侧栏字号对面板内部文字失效」的修复 —— 这块当时漏掉了。

## 四、改动三：自检后台化（用户要求「后台测试，不要影响我使用电脑」）

### 4.1 headless 模式

`--check-ui` 默认**不显示窗口**：

```js
const UI_CHECK_HEADLESS = UI_CHECK && !process.argv.includes('--check-ui-show');
// BrowserWindow: show: !UI_CHECK_HEADLESS, skipTaskbar: UI_CHECK_HEADLESS
// webPreferences: backgroundThrottling: false   // 隐藏窗口会被判为 backgrounded，不关节流会让断言假失败
```

`grab()` 里原本无条件 `win.showInactive()`（会把窗口提上来）→ 改为仅可见模式调用。

报告首行自证：

```
窗口模式: headless（不显示窗口） | isVisible=false
```

### 4.2 踩坑：headless 下截图全空白

第一次跑完发现**所有截图都恰好 4800 字节**（除一张带 `clip` 的 22 KB）—— 统一的字节数就是空白图的特征。

原因：`fromSurface: false` 是从视图取当前合成结果，而 headless 下窗口不参与合成 → 拿到空白。
那张 22 KB 的之所以正常，是因为它走 `clip` 分支，一直用的是 `fromSurface: true`。

修法：

```js
const opts = clip
  ? { format: 'png', clip, fromSurface: true }
  : { format: 'png', fromSurface: UI_CHECK_HEADLESS ? true : false };
```

改完截图恢复到 4–105 KB 的正常体积。

> 排查手法值得记住：**批量产物"大小完全相同"就是异常信号**，比逐张看图快得多。

### 4.3 踩坑：headless 下真实输入事件派发不到

`sendInputEvent`（真实滚轮 / 鼠标移动）在窗口不可见时无效 —— 「真实滚轮 → 画面滚动」三步因此失败。

处理：headless 下这三步标 `SKIP`（不计失败），需要连真实输入一起验时用 `--check-ui-show`：

```js
const SKIP_IN_HEADLESS = new Set(['真实滚轮 → 画面滚动', '注入真实 Ctrl+滚轮', '真实 Ctrl+滚轮 → 缩放']);
```

总结行同步报告跳过数：`UI CHECK: 147 通过 / 0 失败（3 项因 headless 跳过）`。
副作用：headless 下 hover 态截图也看不到（`mouseMove` 注入同样失效）。

### 4.4 踩坑：`App.showTool('ai')` 并不打开 AI 面板

AI 步骤第一次跑，只有依赖**布局宽度**的断言失败了（`输入框 0 / 栏 0`），其余全是 PASS —— 因为面板虽然没打开，DOM 节点照样查得到。

**这是断言设计的陷阱：只断言"节点存在"会让隐藏状态蒙混过关。**

修法：改用 `App.setAiOpen(true)`（幂等，`toggleAi` 会在已开时关掉），并补一条前提断言：

```js
add('AI 面板已展开（以下断言的前提）',
  !!panel && !panel.classList.contains('hidden') && pw > 0, ...);
```

改完 147 项全绿。

## 六、没做的事（明确记录，避免下次又当成"缺口"）

- 不新增 `read_outline` / `read_section` / `create_doc` —— 属于省钱优化，不是能力前提（见第一节）。
- 不加「助手定位」下拉、不动 `run_command` 的注册 —— 编程能力保留。
- AI 面板的对话质量只能靠提示词与模型本身，本次未做任何工具层改造。
