# 079 · M4 收尾：拉取策略 / 安全强推 / 可编辑合并结果 / 远程分支

> 接 `078`（M4 主体）。这一篇把 M4 剩下的四个口子补齐，外加**一个差点酿成数据损失的发现**（§1，最重要）。

## 1. ⚠ 本机 `git rebase` 的 merge 后端会**删掉整个 .git**（必须用 apply 后端）

给"拉取并变基"写回归测试时撞上的：在"有远程、fetch 过"的仓库里执行 `git rebase FETCH_HEAD`，
git 报 `error: could not mark as interactive: No such file or directory`，**退出码还是 0**，然后
**`.git` 目录整个消失**（用 Python 独立进程遍历确认，不是读取问题）。试验 5+ 次全部复现，
C: / D: 盘、原生 init / isomorphic init 的仓库、传 FETCH_HEAD / 传 sha、换 env —— 只要走到这一步就删。

| 写法 | 结果 |
|---|---|
| `git rebase FETCH_HEAD`（默认 merge 后端） | ❌ `.git` 被删 |
| `git pull --rebase origin main`（同样走 merge 后端） | ❌ `.git` 被删 |
| `git -c rebase.backend=apply rebase FETCH_HEAD` | ✅ 正常，历史线性 |
| `git rebase <本地分支>`（无 fetch 场景，078 的冲突用例） | ✅ 正常（冲突停下、abort 也正常） |

**修法**：`git-native.rebase()` 固定带 `-c rebase.backend=apply`，注释里写明"别删这个参数"。
apply 后端冲突时写 `.git/rebase-apply`（不是 `rebase-merge`），进度文件名也不同（`next/last` vs `msgnum/end`）
—— `opState` 两个目录都认、两组文件名都读（这是它第一次写就做对的地方）。

**这是 M4 之后最重要的一条环境结论**：本机 git.exe（绿盾下的不受信进程）除了已知的
"写不进 4 段 ref（refs/remotes/**）"，还会在 merge 后端 rebase 的临时目录创建上失败并连带删掉 `.git`。
顺带：**remote-tracking 引用在本机根本不存在**（`push -u` / `fetch` 后 `refs/remotes/origin/main` 都不会落地），
所以任何"rebase 到 origin/x"的写法在这台机器上都走不通，只能 rebase 到 FETCH_HEAD / 显式 sha。

## 2. Pull 策略（Merge / Rebase / FF-only / 快进）

`pullRemote(dir, { strategy })`：

| strategy | 实现 | 行为 |
|---|---|---|
| `ff`（默认） | isomorphic（**原有路径一字未改**，保留凭证/代理兜底链） | 只在可快进时更新，分叉提示换策略 |
| `ff-only` | 原生 `git fetch --prune` + `git merge --ff-only FETCH_HEAD` | 任何分叉都明确拒绝 |
| `merge` | 原生 fetch + `git merge` | 分叉建合并提交；**撞冲突 → 进 M4 解决流程** |
| `rebase` | 原生 fetch + `git rebase`（apply 后端） | 本地提交重放上去；撞冲突 → 进解决流程 |

UI：`拉取` 按钮改成下拉菜单（四种策略，默认项一键直达），按钮 tooltip 同步。
为什么不在设置里放"默认拉取策略"：默认行为一键直达、非常用的策略收进菜单，误触成本最低。

测试（`tests/git.test.js`，本地 bare 仓库当 origin，不碰网络）：
ff-only 分叉明确拒绝 → rebase 后历史线性（无 Merge 提交）且远程文件进来 → merge 后出现合并提交 → 同步状态再拉 merge/rebase 都"无事可做"。

## 3. 强推：`--force` → `--force-with-lease`

裸 `--force` 会悄悄覆盖别人的提交。`pushForceWithLease`（原生）不带租约参数 =
以「本地记录的远程跟踪引用」为租约：上次 fetch 之后远程又被别人推过 → 推送被拒绝。
推送菜单的"提交并强制推送（--force）"整项替换为"提交并安全强推（--force-with-lease）"，
确认框文案写清两者差别。租约拒绝时的文案：先 ⬇ 拉取看一眼再决定。

## 4. 冲突窗口：三方对比 + **可编辑的合并结果**

之前只能"选一侧"。现在是：

```text
共同祖先（base）│ 当前分支（HEAD）│ 传入的改动     ← 只读对比，各带「用这一份」快捷
──────────────────────────────────────────────
合并结果（可编辑）  [填入共同祖先] [填入当前分支] [填入传入]  [💾 保存并标记为已解决]
┌────────────────────────────────────────────┐
│ <<<<<<< 当前分支（HEAD）                    │   ← 起始 = 工作区里带冲突标记的版本
│ …                                          │      （手工合并最自然的起点：原地改标记）
└────────────────────────────────────────────┘
```

- 结果区**默认填工作区文件**（带 `<<<<<<< ======= >>>>>>>` 标记）—— 懱 git 习惯：想手工拼的人就在标记里改。
- 「💾 保存并标记为已解决」走新通道 `resolveCustom(repo, file, content)`：**写文件 + `git add` 在同一侧完成**
  —— 分两步走（渲染层写文件 + IPC add）会出现"写失败但已 add"的窗口，把空文件/旧内容提交出去。
- 「填入某一侧」只是往编辑区里填内容，不直接解决 —— 决定权在保存那一刻。
- 快捷的「用这一份」（直接选一侧）保留：不想看三方内容的人一步搞定。

自检（`check-ui-1t-m4-conflict.png`）改为走**手工编辑**这条路：断言结果区起始带冲突标记 →
写入手工拼接的内容 → 保存 → 冲突清零 → 文件内容与 index 里的就是拼的那份。

## 5. 分支弹窗：远程分支段 + upstream

`branches()` 现在返回 `remotes`（各 remote 下的分支，`origin/x`）与 `upstream`（当前分支的跟踪关系）。
弹窗里本地分支下面是「远程分支」段，每行 `⋯`：

- **检出为本地分支…**（`git checkout -b <name> <remote/x>`，默认名取 `x`）
- **合并「origin/x」到当前分支 / 把当前分支变基到「origin/x」**（撞冲突进解决流程）
- **设为当前分支的 upstream**（`git branch --set-upstream-to=origin/x`）；当前分支已有 upstream 时，
  段首显示「当前分支跟踪 origin/x [解除]」（`--unset-upstream`）

无本机 git（caps）时远程段只提示"需要本机 git"，不给可点的菜单。
（「对比与当前分支」没进弹窗 —— 日志窗口的 `⇄` 分支对比已经做了这件事，不重复入口。）

## 7. 还剩什么

- 冲突窗口的三方对比仍是只读文本 + 一个编辑区，不是 PyCharm 那种**三栏联动滚动、逐行点击采用**的合并器。
- 本机 remote-tracking 引用不落地 → `push` 的 ahead/behind、`--force-with-lease` 的租约
  都依赖「本地记录的远程跟踪引用」—— lease 在这台机器上**可能永远校验通过**（租约基线不更新）。
  这是环境缺陷，代码无能为力，已记录在案。
