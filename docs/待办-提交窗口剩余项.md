## 1. Changelist（变更列表）· 体量最大

### PyCharm 行为
- 变更列表是**客户端概念**（不落 git），一个仓库可有多份：`Default` + 用户自建；有且只有一个「活动列表」。
- 提交窗口的文件列表**按变更列表分组**，只提交活动列表里被勾选的文件。
- 右键/快捷键 **F6「Move to Another Changelist」**、`Ctrl+Shift+M`，可把文件（或整个列表）移到别处。
- 排除（取消勾选）某文件时，可配置「建议移到其他变更列表」。
- 提交失败时可配置「创建新变更列表」。

### 我们的现状
完全没有。提交窗口是一份扁平列表，勾选集合就是全部。

### 实现方案（建议）
1. **数据**：`<项目根>/.myide/changelists.json`（与 `tasks.json` 同源同思路：随项目走、可进 git、写失败降级 localStorage）。
   结构建议：
   ```json
   { "active": "default",
     "lists": [ { "id": "default", "name": "Default", "comment": "", "files": ["src/a.js"] } ] }
   ```
   注意：**文件不属于任何列表 = 属于 default**（git 工作区是唯一事实来源，列表只记「归属覆盖」）。
   文件从工作区消失时自愈清洗（参考 `tasks.js` 的悬空引用清理）。
2. **渲染**：`fileSections()` 上方再插一层——活动列表正常渲染；非活动列表渲染成 `▸ <列表名> N 个文件`（**不可勾选**，勾了也不能提交，避免误导）。
3. **单文件改动时的归属判定**：`fileRow` 的勾选只动 `checked`；「移入其他列表」改 `changelists.json` 并重渲染。
4. **提交范围**：`doCommit` 里先过滤 `checked ∩ activeList`，其余给一次 toast 提示「N 个文件不在活动列表，未提交」。
5. **UI 入口**：工具行加一个按钮（或放进「分组方式」旁）+ 右键菜单项「移入变更列表…」（弹窗列表 + 新建）。

### 难点 / 风险
- 与「勾选集合是唯一权威」的语义会打架：勾选=暂存，列表=分组。**必须明确文档化**，否则以后自己都会绕。
  建议定死：**列表只影响「显示分组」与「提交范围」，绝不影响 index**；跨列表提交一律不允许。
- 与 `syncChecked()` 的自动勾选/清除联动：新文件默认进 default。

### 验收标准
- [ ] 新建/重命名/删除变更列表，切换活动列表，重启后保持
- [ ] 同一文件移入自定义列表后，不再出现在 Default 组，且提交只包含活动列表内容
- [ ] 非活动列表的文件不可勾选（或勾选无效并有提示）
- [ ] 工作区文件被删除/改名时列表自愈，不残留悬空路径
- [ ] `tests/git.test.js` 覆盖存取与自愈，`tests/dom.test.js` 覆盖分组渲染与移入

## 2. hunk 级暂存 / 取消暂存（部分提交）

### PyCharm 行为
- 在 diff 视图里对单个 hunk 点「Stage/Unstage」，甚至可以在 hunk 里勾选单行（`git add -p` 的图形化）。
- 未暂存区的 hunk 不参与本次提交。

### 我们的现状
只有整文件级别；`commit()` 通过 `resetIndex` 整文件取消暂存。diff 视图（`buildDiffTable`）里 hunk 只支持折叠/展开。

### 实现方案（建议）
isomorphic-git 没有 `add -p`，要自己做「构造部分内容 → 写 blob → 改 index」三步：

1. 取该文件的 `HEAD` 文本 `H`、index 文本 `I`、工作区文本 `W`（已有能力：`blobAt` / `fs.readFileSync`）。
2. 拿到「未暂存 hunk」= `diffLines(I, W)`；用户勾选要暂存哪些 hunk。
3. 从 `I` 出发，把选中的 hunk 应用到 `I` 上得到 `I'`（纯文本操作，`diffLines`/`buildHunks` 已有行号信息）。
4. `const { oid } = await git.writeBlob({ fs, dir, blob: Buffer.from(I', 'utf8') })`
   → `await git.updateIndex({ fs, dir, filepath, oid, mode: 0o100644 })`（新文件用 `add`，删除用 `remove`）。
5. 重新 `status`：文件应变成「暂存+未暂存」混合态（`matrixToStatus` 已有 `*modified` 表示）。

UI：
- diff 视图的 hunk 分隔行加两个按钮「暂存此块 / 取消暂存此块」（`buildDiffTable` 的 `sep` 行）。
- 取消暂存 = 把 index 回退到不含该 hunk 的状态（本质是第 3 步的反向应用）。
- **单行级**（`add -p` 的 `s`/`y`/`n`）先不做，留作下一层。

### 难点 / 风险
- **CRLF / 编码**：写回必须保持文件原有行尾与 BOM，否则会引入整文件假差异（`git-service.status` 里已有 CRLF 误报校验，可复用判断）。
- 行号错位：应用多个 hunk 时要从后往前应用，否则前面插入/删除会移动后面的行号。
- 文件的 `mode`（可执行位）要保留。
- 在 `.gitignore` 忽略的文件上暂存要 `force`。

### 验收标准
- [ ] 单文件多 hunk，只暂存其中一块 → `git status` 显示混合态；提交后 `HEAD` 只含该块
- [ ] 取消暂存能把 hunk 退回工作区，且工作区内容不变（不丢改动）
- [ ] CRLF 仓库（`core.autocrlf=true`）部分暂存后不产生整文件差异
- [ ] 二进制文件 / 超大文件（>20MB，`diffWorkdir` 已限制）不出现暂存按钮
- [ ] 纯文本算法层可单测：`applyHunks(I, hunks)` 放 `git-service.js` 导出，进 `tests/git.test.js`

## 3. 合并冲突节点 + 解决

### PyCharm 行为
- 冲突文件在提交窗口单独一组，红色；右键/双击进三窗格合并工具（Local / Result / Remote）。
- 解决后点「Mark as Resolved」（= `git add`）。

### 我们的现状
应用**根本没有 merge / rebase / stash-pop 能力**（`git-service.js` 里无 merge）。所以：
- 只有从**外部**（命令行/tortoise）产生冲突后再进来，才可能看到冲突状态。
- 做「解决 UI」需要先有冲突来源，否则是无根之木。

### 实现方案（建议，分两步）
1. **只做「检测 + 展示 + 标记已解决」**（低成本、先落地）：
   - 检测：`.git/MERGE_HEAD` / `.git/rebase-merge` / `.git/rebase-apply` 存在 → 处于合并/变基中。
   - 冲突文件：`statusMatrix` 里 `stage` 列缺失但 `HEAD`/`workdir` 有值的行；更可靠的是读 `.git/index` 的 stage 1/2/3 条目
     （isomorphic-git 没有直接 API，需要自行解析 index —— 这一块工作量要单独评估，或退化用「文件里含 `<<<<<<<` 标记」启发式）。
   - UI：分节「合并冲突」置顶 + 红色徽章 `!`；双击用编辑器打开并高亮冲突块（可做一个只读视图）。
   - 「标记为已解决」→ 走现有 `commit()` 的 `git.add`（`force: true` 已有）。
2. **再做「三窗格合并」**（只有第 1 步被真实使用才值得做）。

### 难点 / 风险
- 解析 `.git/index` 二进制格式是独立工作量；先确认用户是否真的会在外部产生冲突。
- 应用目前没有 merge，风险是「做了没人用」。

### 验收标准
- [ ] 外部制造一个冲突后打开提交窗口，出现「合并冲突」节且不计入普通「更改」
- [ ] 冲突中（`MERGE_HEAD` 存在）时提交按钮给出明确提示，不产生半成品提交
- [ ] 「标记为已解决」后文件回到普通「更改」节

### 前置决定（需要用户拍板）
**要不要给应用加 merge 能力？** 不加，本节就只是「外部合并后的收尾工具」；加，就是另一个大工程。

## 4. 提交前检查（Before Commit）

### PyCharm 行为
提交窗口底部（旧版为弹窗内）有可勾选的「提交前」动作，配置持久化：

| 项 | 作用 |
|---|---|
| Reformat code | 按项目代码风格重排格式 |
| Rearrange code | 按 arrangement 规则重排成员顺序 |
| Optimize imports | 删掉多余 import |
| Analyze code | 用 inspection profile 静态检查，问题进提交前提示 |
| Check TODO (filter) | 按 TODO 过滤器检查 |
| Cleanup | 应用当前 profile 的清理 |
| Run Git hooks | 跑 `.git/hooks/pre-commit` |

### 我们的现状
无。且**没有格式化器、没有静态分析器、没有 import 优化器**（这是纯前端 Electron 项目，没接 prettier/eslint 到运行时）。

### 实现方案（建议，按可行性分档）
**能做的（真实有效，建议先做）**
1. **提交消息校验**：非空 + 可选「长度 ≤ 72」+ 可选正则（配置存 `myide-git-ui` 那类 localStorage）。空消息目前已有拦截，补正则与字数提示。
2. **Check TODO**：对即将提交的文件做正则扫描（`TODO|FIXME|XXX|HACK`），列出文件:行号，可「仍然提交」。
3. **Sign-off**（见第 5 节）。
4. **Run Git hooks**：isomorphic-git **不跑** hooks。要做只能自己在主进程 `child_process.spawn` 执行 `.git/hooks/pre-commit`，并处理退出码/输出。**这是一个真实的认知差**，值得做，但要处理 Windows 下 shell 脚本的执行（`sh`/`bash` 是否存在）。

**需要引工具链才做的（先别做）**
- Reformat / Optimize imports / Analyze：四个语言（JS/TS/Python/MD）各一套，等于把 IDE 的 lint 层重做一遍。
  **建议明确写下不做**，避免以后被「PyCharm 有」推着做半成品。

### 验收标准
- [ ] 「提交前」折叠区可配置并持久化，勾选项在提交前依次执行
- [ ] TODO 检查能列出命中项并可继续提交
- [ ] pre-commit hook 非 0 退出 → 提交中断且显示 hook 输出
- [ ] 消息正则不满足 → 阻止提交并给出原因

## 5. Sign-off / 作者覆盖（成本最低，可随时做）

### PyCharm 行为
- 「Sign-off commit」勾选后，在提交消息末尾自动追加 `Signed-off-by: Name <email>`（DCO）。
- 提交窗口右上「Author」下拉可改本次提交作者（替别人提交）。

### 我们的现状
- `git-service.commit(dir, { message, files, amend, author })` **已经接受 `author` 覆盖**（上一轮加的参数，目前没人用）。
- 提交消息框没有 Sign-off 开关，UI 也没有作者选择器。

### 实现方案
1. UI：amend 那一行加「Sign-off」复选框（持久化）；勾上时提交前追加签名行（避免重复追加）。
2. 作者：`openCommit` 旁加一个下拉/输入，默认 `getUserConfig(root)` 的 name/email，可临时覆盖（**不写回 git config**）。
3. 消息历史里的签名行——按 PyCharm 行为，签名是提交时追加、不写进输入框（或写进去但去掉重复）。

### 验收标准
- [ ] 勾 Sign-off → `git log -1 --format=%B` 末行是 `Signed-off-by: ...`
- [ ] 重复提交不会出现两遍签名
- [ ] 作者覆盖只影响这一次提交，git config 未被改写

## 7. 建议的实施顺序与理由

| 顺序 | 项 | 理由 |
|---|---|---|
| 1 | Sign-off / 作者覆盖（第 5 节） | 半成品已有（`commit()` 支持 author），一天内能收口，收益立刻可见 |
| 2 | 提交前检查里「能做的」那三项 + Git hooks（第 4 节） | 不依赖外部工具链，且能立刻防住「空消息/漏 TODO/hook 被绕过」 |
| 3 | Changelist（第 1 节） | 纯客户端逻辑，不碰 git 对象层，风险可控；但需要先定死与「勾选=暂存」的语义边界 |
| 4 | hunk 级暂存（第 2 节） | 收益大但要动 blob/index + CRLF/编码，需要先把 `applyHunks` 的纯函数与单测做扎实 |
| 5 | 合并冲突（第 3 节） | 需要先决定「应用要不要有 merge 能力」，否则先只做「检测 + 标记已解决」 |
| — | Reformat / Optimize imports / Analyze | **建议明确不做**（需要引入完整 lint/format 工具链），在文档里记一笔即可 |
