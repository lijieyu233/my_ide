## 一、这次到底出了什么问题

现象：

```
git push origin main
fatal: could not read Password for 'https://lijieyu233@github.com': terminal prompts disabled
```

以及推成功之后的怪事：

```
git status -sb
## main...origin/main [ahead 27]      ← 明明已经推上去了
git fetch origin
   c4c6566..ecd4662  main -> origin/main   ← 看起来成功
git status -sb
## main...origin/main [ahead 27]      ← 还是没变
```

**两个独立问题叠加**，而且第二个极具迷惑性（会把人引向"网络/代理/凭据/分支名"的错误方向）：

| # | 问题 | 本质 |
|---|---|---|
| A | `git push` 报"读不到密码" | **凭据**：GCM 里没有 github.com 凭据 |
| B | 推成功后 `status` 显示假的 ahead、`fetch` 无效 | **本机缺陷**：git 写不进 `.git/refs/remotes/**` |

---

## 二、问题 A：凭据（已永久解决）

### 排查结论（都是实测，不是猜）

| 检查项 | 结果 |
|---|---|
| `credential.helper`（全局） | GCM（git-credential-manager） |
| GCM 里有没有 github.com 凭据 | **没有** |
| `~/.git-credentials` | 只有 Gitea `134.175.67.86:3000`（用户 `reed`）一条 |
| 代理 `http://127.0.0.1:10808` | 可连接（gitconfig 已配给 github.com） |
| `github.com` | 能解析 |
| `gh.exe` | **`D:\software\gh-cli\bin\gh.exe` 已登录** `lijieyu233`，scope `repo`/`gist`/`workflow` |

→ 网络、代理、协议、分支名全都正常，**纯粹缺凭据**。

### 修法（已写入全局配置，永久生效）

只给 `github.com` 换助手，**不动 Gitea 等其它主机**：

```bash
git config --global --replace-all credential.https://github.com.helper ""
git config --global --add credential.https://github.com.helper '!D:/software/gh-cli/bin/gh.exe auth git-credential'
git config --global --replace-all credential.https://gist.github.com.helper ""
git config --global --add credential.https://gist.github.com.helper '!D:/software/gh-cli/bin/gh.exe auth git-credential'
```

- 第一行空值的作用是**清掉该主机上的 GCM**（gitcredentials 明确规定：空串会重置该上下文的 helper 列表），
  否则 GCM 仍会先被问到并弹出 GUI。
- 用 host-scoped 的 `credential.<url>.helper` 而不是改全局 `credential.helper`，是为了**不影响 Gitea**。

### 效果

```bash
git push origin main          # 不带任何 -c 参数，直接就能推
```

## 三、问题 B：git 写不进 `.git/refs/remotes/**`（已定位 + 已修）

### 症状为什么容易误判

- `git update-ref refs/remotes/origin/main <sha>` → **rc=0**（成功！）
- `git fetch` → 打印 `c4c6566..ecd4662 main -> origin/main`（成功！）
- reflog `.git/logs/refs/remotes/origin/main` **确实被更新了**

但 `.git/refs/remotes/origin/main` 这个文件**根本不存在**，于是 `git rev-parse origin/main`
只能回退到 `packed-refs` 里的旧值 → `status` 永远显示假的 ahead。

### 对照实验（决定性证据）

| 谁写 | 路径 | 结果 |
|---|---|---|
| git | `refs/heads/*`（3 段：`refs/A/B`） | ✅ 落地，git 读得到 |
| git | `refs/zz/x`、`refs/origin-rt/main`（3 段） | ✅ |
| git | `refs/remotes/<remote>/<branch>`（**4 段**：`refs/A/B/C`） | ❌ rc=0 但**文件不落地** |
| git | `refs/rt/origin/main`、`refs/zz/yy/x`（4 段） | ❌ |
| Python / Node | 任意路径，含 `refs/remotes/**` | ✅ 落地，且 **git 能正确读到** |

关键点：

1. **与「段数」相关**：git 能写 3 段（`refs/A/B`），写不了 4 段（`refs/A/B/C`）。
2. **与进程相关**：同样路径，受信进程（Python/Node）写就正常。这与本机绿盾 TSD
   「不同进程看到的文件可能不同」是同一类现象，只是这里表现为**不受信进程（git.exe）的写入不落地**。
3. 目录属性查过：不是 junction、不是加密属性、ACL 正常（Python 在里头建文件毫无问题）。

### 修法（已验证两次）

> **把 `.git/refs/remotes` 整个目录挪出 `refs/` 之外，再让 `git fetch` 自己重建。**

要点（踩过坑的）：

- 必须**整个挪走**，不能只清空——原地留一个**空目录**反而会复现问题。
- 备份目录要放到 `refs/` **之外**（如 `.git/git-doctor-backup/`）；把 `_remotes_bak` 这类残留目录
  留在 `refs/` 下面会让 git 继续写不进。
- 引用数据本身不丢：它们同时存在于 `packed-refs`，且可以重新 fetch。

验证（当时输出）：

```
refs/remotes/origin/main: 存在=True 值=515a3feaa672
refs/remotes/origin/dev : 存在=True 值=02c0c63097a0
git rev-parse origin/main = 515a3feaa672
git status = ## main...origin/main        ← 假的 ahead 消失
```

### 走过的弯路（别再试）

- ❌ **`reference-transaction` 钩子自动补写**：钩子确实会触发（git 2.55，
  `preparing`/`prepared`/`committed` 三态齐全），Node 也报告"补写成功"，
  但事后文件还是不存在（git 在事务收尾时会清掉）。而且给每次引用事务都挂一个子进程，开销和副作用都不划算。
  最终**没有采用**，钩子已删除。

---

### 结构性修复（推荐，一劳永逸）：把跟踪引用挪到 git 写得进去的命名空间

上面"挪目录"能修，但**每次 `git push` 都会把本地跟踪引用擦掉**（实测：裸 push 成功后
`refs/remotes/origin/main` 又没了，`status` 变成 `[gone]`）——因为 push 也要更新跟踪引用，
而 git 写那个 4 段路径依然会失败。

所以真正的解法是**让 git 不用写 4 段路径**：

```bash
git config --local remote.origin.fetch '+refs/heads/*:refs/rt-origin/*'
git config --local branch.main.merge refs/heads/main
git config --local branch.main.remote origin
```

`refs/rt-origin/<branch>` 是 **3 段**，正是 git 在本机能正常写的形态。改完之后：

```
git fetch
 * [new branch]  main -> refs/rt-origin/main     ← 文件真的落地了
 * [new branch]  dev  -> refs/rt-origin/dev
git rev-parse @{u}   → 01b93864978a...           ← upstream 正确解析
git status -sb       → ## main...rt-origin/main  ← ahead/behind 可信，不再有假的 ahead / [gone]
```

要点：

- 用 **host/local 配置**即可（本仓库 `.git/config`），不污染全局、不影响别的仓库。
- `branch.<name>.merge / .remote` 要补上：跟踪引用的名字是 git 用 `remote.<r>.fetch` 的 refspec
  把 `refs/heads/<branch>` 映射出来的，`@{u}` 也走同一套映射。
- **副作用**：`origin/main` 这类写法不再存在（变成 `rt-origin/main`）。
  明确知道这一点就好，`git log origin/main..HEAD` 要写成 `git log rt-origin/main..HEAD` 或直接用 `@{u}`。
- `git push` 不受影响：推送的目标 ref 名在远端，跟本地 fetch refspec 无关。

## 四、体检与自愈工具

`scripts/git-doctor.js`（`npm run git:doctor`）：

```
[1] 推送凭据      —— github.com 助手是否指向 gh、gh 是否已登录
[2] 远端跟踪引用  —— 用 git ls-remote 的真实值比对本地 refs/remotes/*
                   不一致时自动：归档 refs/remotes → git fetch 重建 → 复查
[3] 当前状态      —— 打印 status / ahead-behind，并提醒"别信本地 ahead/behind"
```

```bash
node scripts/git-doctor.js            # 检查并自动修复
node scripts/git-doctor.js --check    # 只检查不改动
node scripts/git-doctor.js upstream   # 指定远程
```

实测：

- 健康态 → `全部正常 ✅`
- 人为破坏（把 `refs/remotes` 变成空目录）→ 检出 `2/2 个引用缺失` → 自动归档 + fetch → `修复后引用一致`

实现方式上的两条硬约束（本机环境）：

1. **不用 `fs.rmSync`**：本环境 `rm` 和 `fs.rmSync` 都被安全删除垫片接管（会抛错且不删）。
   脚本只用 `renameSync` 归档，绝不删东西。
2. **不信任本地 ahead/behind**：最终判断"推没推上去"一律用
   `gh api repos/<owner>/<repo>/branches/<branch> --jq .commit.sha` 或 `git ls-remote`。

## 五、以后推 GitHub 的标准动作

```bash
cd D:/document/code/tools/my_ide

# 1（可选）体检：推之前/出问题之后跑一下
npm run git:doctor

# 2 正常提交（message 用 <类型>: <中文说明>）
git add <显式列路径，不要 git add .>       # kiosk_patches/ 不属于本仓库
git commit -m "feat: ..." -m "明细 + 测试结果"

# 3 直接推，不需要任何 -c 参数（凭据已永久配好）
git push origin main

# 4 验证（不要只看 git 的输出）
"D:/software/gh-cli/bin/gh.exe" api repos/lijieyu233/my_ide/branches/main --jq .commit.sha
```

### 出问题时按这个顺序看

| 报错 / 现象 | 先看 | 处理 |
|---|---|---|
| `could not read Password for 'https://<user>@github.com'` | 凭据 | `npm run git:doctor` 第 [1] 节；本文第二节 |
| `getsockname() failed with errno 10022` | 网络栈被绿盾拦 | 启动 `node D:\software\gh-cli\git-proxy.js`，然后 `git -c http.proxy=http://127.0.0.1:17890 push` |
| `Permission denied`（22/443） | 用了 SSH | 换 HTTPS：`https://lijieyu233@github.com/lijieyu233/<repo>.git` |
| `src refspec master does not match any` | 分支名 | `git branch --show-current`，需要时 `git init -b main` |
| 推成功但 `status` 显示 ahead / `fetch` 没反应 | **本机缺陷 B** | `npm run git:doctor`（自动归档 + fetch 重建） |
| `git credential fill` 弹 GUI 卡住 | 别跑这个命令 | 设 `GCM_INTERACTIVE=never`；排查凭据改用 `gh auth status` |
