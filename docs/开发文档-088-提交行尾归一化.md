# 开发文档-088 · 提交时的行尾归一化（autocrlf 仓库不再把 CRLF 写进仓库）

> 起因：排查一条**变红的旧回归测试**时顺出来的真缺陷。
> `pull` 那条测试的「夹具前提②」突然不成立了，追下去发现它成立的年代已经过去，
> 而顺着同一个根因往下走，**提交路径上还留着另一半没修** —— 那一半会让仓库里的行尾是错的。
> 这一篇记的是**现象 → 取证 → 根因 → 修法 → 反向验证**，以及"夹具前提失效"该怎么读。

## 0. 现象：一条测试红了，但它红的不是产品

`npm run test:git` 出现 **60 通过 / 1 失败**：

```
FAIL pull：ff 快进必须真的落盘（autocrlf 仓库不再"refs 走了、工作区没走"）
  -> 夹具前提②：isomorphic 必须把这份 CRLF 工作区误判成已修改（这正是不落盘的根因），
     matrix=["a.txt",1,1,1]
```

注意失败信息是**夹具前提**，不是断言本身。文档 084 §5 特意把前提做成显式 assert，
就是为了让这种情况一眼可辨：**不是产品坏了，是"复现这个 bug 所需的环境"不再成立**。

## 1. 取证：前提② 为什么失效了

084 制造 stat 失效的手法是「删掉文件 → `git checkout -- <file>` 从 index 恢复」，
靠的是"checkout 写文件必然晚于 `.git/index` 落盘"这个时序。实测把这一步单独量出来：

```
工作区内容 = "l1\r\nl2\r\n"
恢复后 stat: mtimeMs=1790788986601.9087 ctimeMs=1790788986601.9087 size=8
.git/index mtimeMs=1790788986601.9087
mtimeMs < indexMtimeMs ? false          ← 同一毫秒
statusMatrix = [["a.txt",1,1,1]]        ← 没被误判
原生 git status --porcelain = ""        ← 干净
```

**mtime 与 index 落在同一毫秒**（本机 NTFS + 较新 Node 的文件时间戳精度足够高），
于是 isomorphic-git 的 `compareStats`（比 `mtimeSeconds`/`ctimeSeconds`/`ino`/`size`）
判定"stat 吻合" → **直接信 index 里的 oid，根本不读盘重算** → 前提② 不成立。

> 也就是说 084 那套手法**依赖一个不可靠的时序**，它能红是"当年恰好晚了一毫秒"。
> 修法是显式把 mtime 推后（`fs.utimesSync`，等价于"编辑器保存过这个文件"），把前提钉死。
> 补一次 `git update-index --refresh` 也不行 —— 实测仍然 `[1,1,1]`。

## 2. 顺着根因往下：提交路径上的另一半没修

084 修的是 **index → 工作区**（checkout / pull 落盘）；`git-native.js` 里 `checkout` 的长注释
记的是同一个根因。那么**反方向**呢 —— **工作区 → index**（`git add`）？

`git-service.js` 里 5 处 `git.add` 全走 isomorphic-git，而它的 `FileSystem.read` 只在
`options.autocrlf === 'true'` 时才做 `\r\n → \n`：

```js
// node_modules/isomorphic-git/index.cjs
async read(filepath, options = {}) {
  let buffer = await this._readFile(filepath, options);
  if (options.autocrlf === 'true') {            // ← 这个值从哪来？
    ...buffer.replace(/\r\n/g, '\n')...
```

而 `autocrlf` 来自 `GitConfigManager`，库内注释明写**只能读写本地 `$GIT_DIR/config`**。
真实机器上 `core.autocrlf` 通常只在**全局** `~/.gitconfig`（本机就是，见 084 §2）
→ 它读到 `undefined` → **不归一化** → 把工作区的 CRLF 字节原样算 sha1 写进 index。

### 实测对照（同一份 `l1\r\nl2\r\n`）

| | `git ls-files --eol` | HEAD blob |
|---|---|---|
| **修复前** MyIDE `commit()` | `i/crlf  w/crlf` | `"l1\r\nl2\r\n"`（**含 CR**） |
| 原生 git（对照） | `i/lf    w/crlf` | `"l1\nl2\n"` |

**这是数据损坏级别**，不只是显示问题：提交进仓库的是 CRLF 版本，协作者与 CI 会看到整文件重写，
而且**别人检出后再提交会把行尾来回翻转**（每次翻转都是一个无意义的提交）。

## 3. 修法：`git add` 也走原生优先

沿用 084 / `git-ops.js` 已经确立的路子 —— **原生优先、无本机 git 回落**：

1. `git-native.js` 新增 `addPath(repo, file, force)`：跑 `git add [--force] -- <file>`，
   与 isomorphic 语义对齐（`--force` = PyCharm 勾选被忽略的文件时的强制加入），
   路径走 `--` 分隔杜绝以 `-` 开头的文件名被当成选项。
   顺带加了 `unstagePath`（`git rm --cached`），并把"为什么 `git.remove` 不用走原生"
   （它只写 index 条目、不哈希工作区内容）写在注释里。
2. `git-service.js` 新增唯一入口 `stageFile()`：`nativeAvailable()` 为真走原生，
   失败/不可用回落 isomorphic（**不能因为没装 git 就让提交失败**，那会丢用户的工作）。
   5 处 `git.add` 全部改走它：`commit()` 两处（暂存勾选 + 提交后拉回 index）、
   `revertCommit`、`cherryPick`、`shelveCreate`。
   `commit()` 里那处顺手从"静默忽略失败"改成**抛错进事务回滚**（暂存失败不该假装提交成功）。

### 踩到的坑：`probe()` 的字段是 `available` 不是 `ok`

第一版 `nativeAvailable()` 写的是 `p.ok` —— `probe()` 返回的对象里**根本没有 `ok`**
（字段是 `available` / `exe` / `version` / `caps`），于是表达式恒为 `undefined` →
**永远回落 isomorphic，修复完全没生效**，而语法检查、其他测试全都照常通过。
是拿复现脚本重跑时看到 `ls-files --eol` 仍是 `i/crlf` 才发现的。
所以这条修法的**判据必须是"仓库里的字节"**，不能是"代码改了"。

## 4. 反向验证（照 084 §5 的规矩）

新增回归测试：

```
行尾归一化：autocrlf 仓库（只有全局配置）提交后 index 与 HEAD 都是 LF
```

四条断言：① index 是 `i/lf`（工作区仍是 `w/crlf`）；② `HEAD:crlf.txt` 不含 CR；
③ 工作区文件**一个字节都没被改写**（归一化只作用于 index）；④ 原生 git 认为干净。

然后**把修复短路一次**（临时强制 `stageFile` 走 isomorphic），确认它真的会红：

```
FAIL 行尾归一化：autocrlf 仓库（只有全局配置）提交后 index 与 HEAD 都是 LF
  -> index 里应存 LF（i/lf），实际: "i/crlf  w/crlf  attr/  \tcrlf.txt"
结果: 61 通过, 1 失败
```

报错信息直指根因（`i/crlf` vs `i/lf`），恢复修复后转绿。**这条测试守得住这个 bug。**

> 无本机 git 的机器上这条记 **SKIP** 而不是 FAIL —— 回落实现（isomorphic）**做不到**归一化，
> 这是已知能力差距，不该在没装 git 的机器上假红。

| 项 | 结果 |

| `npm run test:git` | **62 通过 / 0 失败**（原 60+1 红） |

## 6. 可复用的结论

1. **"夹具前提"失败 != 产品坏了**。把前提写成显式 assert 的收益，就是能在这一刻立刻分辨
   是"bug 没了"还是"环境变了"。前提依赖**时序**（mtime 与 index 谁先谁后）时尤其脆 ——
   要么用 `utimesSync` 这样的显式手段钉住，要么承认它不可靠。
2. **同一个根因要往两个方向各查一遍**。084 修了 index→工作区，反方向的 工作区→index
   没人看，于是同一条 bug 换个方向继续损坏数据。`git-ops.js` 里 `checkout` 的注释
   已经把这个根因写得很清楚了 —— **它其实就是"下一条路径也必坏"的预言**。
3. **判据要用外部可观测的事实**。这次如果只看"代码改了 / 测试绿了"就收工，
   `p.ok` 那个笔误会让修复**完全没生效**却一路绿灯。用 `ls-files --eol` 这种
   仓库里的真实字节做判据，才在第一时刻暴露出来。
