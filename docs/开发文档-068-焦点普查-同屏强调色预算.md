# 开发文档-068 · 焦点普查（同屏强调色预算）

> 起因：用户说「我看了下 vscode 他的展现也很乱」。
> 这句话推翻了前几轮隐含的前提（"对着 PyCharm 补差距就行"），于是先把判据定下来，再量化。

## 一、判据：两个轴

```
乱 = 元素密度 × 区域明度差
```

| | 明度差大 | 明度差小 |
|---|---|---|
| **元素多** | 密而不乱（PyCharm） | **乱**（VS Code 默认） |
| **元素少** | 清爽（本项目的目标位） | 粘 / 糊（本项目改前） |

- VS Code 的乱来自「功能密度 + 区域几乎同色」——**不是元素多本身**。它是主动选择的中性：
  要适配无数扩展与语言，只能把定制权交出去，代价是默认观感偏平。
- PyCharm 元素一样多却清楚，靠的是工具窗口 / 编辑器 / 外框之间明确的明度差。
- 前几轮我在调**元素**（改图标、删按钮、收项目栏），那动的是横轴；而我们的问题一直在**纵轴**。

**结论（写进项目记忆）**：不要再靠"加 / 减元素"解决观感问题。只问两件事 ——
这块区域和旁边那块**明度差几级**？同屏**有几个东西在抢注意力**？

## 二、量化：新增自检步骤 `focusCensus`

第二问正是这次要量化的东西：**同屏有多少个元素在用强调色"喊"**。

判定口径（`scripts/check-ui-steps.js`）：

| 分类 | 判据 |
|---|---|
| **强焦点** | 实心 accent 填充（α≥0.5 且面积 ≥150px²）／ ≥2px 的 accent 边或伪元素条 ／ accent 阴影（`box-shadow: inset 2px…`）／ 大号粗体 accent 文字（≥13px 且 weight≥600）／ **强调图标按钮** |
| **弱（仅提示）** | 半透明 tint 背景（α<0.5）、1px 边框、普通正文里的 accent |

- 浮层（菜单 / 弹窗 / 待确认浮层 / 空状态）**不算「同屏」** —— 它们的出现是用户主动触发的，不是常驻视觉。
- **按「载体」计数**：已计入元素的后代不再重复计数（`.tool-btn.active` 的 svg 图标会继承 accent color，
  不排除的话同一个提示会被数三遍）。

## 三、顺手挖出的真 bug：颜色解析器不认 hex

第一次跑出来是「**强=33**」，清单里 `#toolbar`（1380×38）、`#sidebar`、`#tabbar`、`#panel-title`
全被算成"accent 实心块" —— 一眼就是错的。

根因：

```js
// 旧写法（两处）
const nums = (String(str).match(/[\d.]+/g) || []).map(Number);
```

`getComputedStyle` 读自定义属性返回的是 **`#f06292` 这种写法**，而正则只抓数字 →
`'#f06292'.match(/[\d.]+/g)` = `['06292']` → `[6292]` → 长度不足 3 → **返回空数组**。
于是 `A`（accent）成了 `[0,0,0,0]`，再拿任何颜色与它比"距离 ≤42" —— **所有深色都匹配**。

**连带影响（更严重）**：主题步骤里几个用 `spreadOf()` 的断言**一直是空转的** ——
`spreadOf('#212121')` 恒为 `-1`，而断言写的是 `spread > 3` → 永远 false、"有偏色"永远不报：

- `每个主题都满足各自的明度阶梯规则`（tint 那一半）
- `石墨主题的底色是中性黑灰（红只做强调色，不做环境光）`
- `石墨主题正文色也中性`

即：**这几条"全绿"是假的**。已换成能认 hex / `rgb()` / `rgba()` / `color(srgb …)` 的解析器，
并保留一段注释说明为什么必须认 hex。

> 教训：**解析器的输入格式要想清楚**。断言写错会失败，至少看得见；
> 解析器写错会"永远通过"，看不见 —— 比没有断言更糟。

## 四、两个检测盲区（补上后结论不变）

1. **`box-shadow: inset 2px 0 0 accent`** —— 树行 focus、弹窗选中项都是这么写的。只查 `border` 会看不见。
2. **强调图标按钮** —— 强调色在 `color`（SVG 用 `currentColor`），而且它**有子节点**；
   原来那条"只查无子节点的文字"的规则会漏掉所有强调图标按钮。

补上后仍是 `强=3` —— 说明这个结论不是靠漏检换来的。

## 五、基线必须是干净的

第一次量到的是「强=3 / 弱=16」，但截图显示 AI 面板里躺着前几步残留的 3 条历史消息和一个待确认浮层。
**那量的是"跑了一半的调试状态"，不可复现。**

普查第一步先清残留：关掉待确认浮层（`#cr-no` / `#dw-no`）+ 新建会话（`#ai-new`），
并加一条自证断言 `基线干净：AI 面板无历史消息、无待确认浮层`。
之后弱用从 16 → 20（空状态的引导卡片与快捷按钮会用到 accent tint），去重后落到 **6**。

## 六、结果：不需要减

```
强焦点 = 3   [tool-strip×1  sidebar×1  tabbar×1]
弱提示 = 6   [toolbar×1  tabbar×1  ai-panel×3  statusbar×1]
```

| 区域 | 强焦点 | 是什么 |
|---|---|---|
| 左侧工具条 | 1 | `#tool-project.tool-btn.active` 的 2px 左线 |
| 侧栏 | 1 | `.tree-row.selected::before` 2×22 竖条 |
| 标签栏 | 1 | `.tab.active` 的 2px 上边线 |
| AI 助手 | **0** | 强调色只以 tint / 细边出现 |
| 工具栏 / 状态栏 | 0 | 当前项目用 `accent 42%` 边线 + `15%` 底（弱） |

**三个强焦点全是"当前项指示器"，每个区域正好一个 —— 这正是想要的形态。**
所以这一轮没有改任何样式：普查的价值是**证明"已经在目标位上"，并把它锁住**。

顺便确认了一件事：**我们不需要靠删功能来变清楚**。我们的元素数天生比 PyCharm / VS Code 少
（不做调试器、不做终端、不做扩展市场），所以只要明度差（纵轴）到位就够了 ——
这也解释了为什么「区域用缝 + 明度四档」那一轮的效果比之前所有图标改造加起来都明显。

## 七、守卫（3 条永久断言）

```
PASS  每个区域最多 1 个 accent 强焦点（一个区域只该有一个"当前项"）   [tool-strip×1 sidebar×1 tabbar×1]
PASS  同屏 accent 强焦点总数 ≤ 4                                    [强=3]
PASS  accent 的弱用（载体数）不超过 10 处                            [弱=6]
```

阈值都留了余量（3≤4、6≤10）—— 这是"强调色有没有在当环境光用"的**粗筛**，不该卡在临界值上造成假警报。

## 九、过程中踩的坑

- 补丁脚本用 `python -c` 内联时，`"` 与 `\` 反复被吃（`assert` 直接 SyntaxError）。
  已按项目惯例改成"先 Write 成 `.py` 再跑"，但**这轮又踩了一次**：`NEW4 = ("…\"强调色…\"…")`
  里用了半角双引号，Python 直接报语法错。
- 补丁的锚点要按**当前文件内容**取（`pc` 前面我加过一行注释，旧锚点就 0 匹配）。
- `&&` 链在补丁失败时会断掉，而后面用 `;` 接的启动命令**照样会跑** →
  于是循环读到的是**上一轮的报告**，一度把旧结果当新结果看。
  **判活/判新一律看报告里的新断言是否存在（或时间戳），不要只看文件是否存在。**
