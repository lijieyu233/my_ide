# 开发文档-084 · 拉取（快进）不再"指针走了、工作区没走"

> 起因：用户原话 ——「我刚拉下代码怎么就显示有更改」。
> 一次「拉取（快进）」之后，提交窗口冒出一屏 10 项"更改"，没有一项是他改的。
> 这一篇记的是**现象 → 取证 → 根因 → 修法 → 怎么守住**，因为根因藏在依赖库的两步之间，
> 而且第一版回归测试是**假绿**的（见 §5），那个教训比结论更值得留。

## 0. 现象

拉取后 `git status` 的 10 项**全在第一列**（已暂存），提交窗口按自己的分组规则摊成两组：

| 面板分组 | 内容 | 共同点 |
|---|---|---|
| 更改 7 个文件 | `开发文档-083-….md`（删除）+ 6 个文件 | 除文档外**全是 CRLF** 文件 |
| 已暂存（外部）3 个文件 | `AGENTS.md` / `md-editor.js` / `styles.css` | **全仓仅有的 LF 文件** |

这个"LF/CRLF 恰好把两组分开"的巧合，是后来定位根因的第一条线索。

## 1. 取证：先确认"这不是用户的改动"

三条互相独立的证据，缺一不可：

1. `git ls-remote --heads origin dev` == 本地 `HEAD` == `c7cdd1a` —— 远端提交**已经进了** `.git/objects`；
2. `git write-tree` == `15a8c281^{tree}`，且 `git diff --stat 15a8c281` **为空**
   —— 磁盘与暂存区**完整等于旧提交**，一个字节的编辑都没有；
3. `git status --porcelain` 里 10 项**全在第一列**（`M `/`D `，第二列全空）—— 全是"已暂存"，
   所以面板把它们画成只读的「已暂存（外部）· 保持不动」。

即：**refs 前进到了最新提交，但工作区/索引停在旧快照**，两者的差集被显示成了"更改"。

## 2. 根因：isomorphic-git 的 `pull` 是两步，第二步失败了

`git-service.js` 的 `pullRemote` 默认策略 `ff` 走 isomorphic-git 的 `git.pull`，它内部是：

```
_pull  =  _fetch  →  _merge(fastForward)  →  _checkout
                        ↑ 只写 ref            ↑ 真正落盘
```

- `_merge` 的快进分支**只 `writeRef` 就 return，完全不碰工作区**
  （`node_modules/isomorphic-git/index.cjs` 的 `_merge`：`writeRef` 后直接返回 `{oid, fastForward:true}`）；
- 真正把文件写到磁盘的是紧随其后的 `_checkout`；
- 而那个 `_checkout` **不认 autocrlf**（同一个坑 2026-09-28 已在**切换分支**上踩过，
  见 `git-native.js` 里 `checkout` 的长注释）：它拿工作区磁盘字节直接算 sha1，
  与 index 里归一化后的 LF blob 一比 → 判定"有本地改动" → 抛 `CheckoutConflictError`。

于是：**refs 走了，工作区没走**，`git status` 于是列出 HEAD 与旧快照的全部差异。

### 为什么偏偏是这台机器

本仓 `core.autocrlf=true` **只写在全局 `~/.gitconfig`**（`.git/config` 里没有），而
**isomorphic-git 只读仓库本地 `$GIT_DIR/config`**（库内 `GitConfigManager` 注释明写"目前只能读写本地"）。

⚠ 这条差异是致命的：**本地一写 autocrlf，isomorphic 就会自己归一化，bug 反而消失**。
第一版回归测试正是因为把 autocrlf 写进了本地 config 而变成假绿（见 §5）。

### 复现（照原样重放两步）

在临时副本里把状态还原成"拉取前"（`HEAD`/index/工作区都在 `15a8c281`），再重放 `_merge` → `_checkout`：

```
① merge      : {"oid":"c7cdd1a1…","fastForward":true}      ← ref 走了
   index     : 30a630b6 (应仍是旧树)                        ← 索引没走
② checkout   : 抛错 -> CheckoutConflictError
   dev ref   : c7cdd1a                                     ← 指针停在新的
   index     : 30a630b6                                    ← 索引仍是旧的
== 最终 git status ==
M  AGENTS.md
D  "docs/开发文档-083-Markdown实时预览与预览对齐.md"
M  main.js   … 共 10 项
```

**与用户截图逐项一致**（含那条被删的文档）。

## 3. 修法：fetch 留 isomorphic，落盘交给原生

`pullRemote` 的 `ff` 分支改为两段：

1. **fetch 仍走 isomorphic**：应用「远程仓库」弹窗里存的凭证是经 `auth` 传进来的，
   **只有这条路认**；原生 git 只认系统凭证助手（gh CLI）。用户若只在弹窗里填过 token，
   整条拉取就会拉不动。代理同理（后端已注入 CONNECT 隧道）。
2. **快进合并走原生 git**（`nativeGit.merge(root, head, {ffOnly:true})`）：
   原生 git 先做行尾归一化再比对，**只在真有本地改动时拒绝**，
   且拒绝发生在**移动 ref 之前** —— 不会再产生"指针走了、文件没走"的半吊子状态。

取不到本机 git 时退回 isomorphic 老路径（那条在 autocrlf 仓库上无解，属已知降级）。

> `git checkout` 通道早在 2026-09-28 就修成了「原生优先」（`git-ops.js` 里唯一同时写
> `op` + `native` 的通道）。**`pull` 漏了这层兜底** —— 它绕过了那个通道，自己调了 isomorphic 的
> 内部 checkout。所以这不是新坑，是**同一个坑在另一条路径上复发**。

顺手把两类拒绝文案说清楚：分叉 → 引导换「合并 / 变基」；真有未提交改动 → 明说"先提交或暂存"。

## 4. 验收

| 项 | 结果 |
|---|---|
| `npm run check:js` | 27 个文件全部通过 |
| `npm run test:git` | **61 通过 / 0 失败** |
| `npm run test:dom` | **269 通过 / 0 失败**（AGENTS.md 基线） |
| 新增回归测试 | `pull：ff 快进必须真的落盘（autocrlf 仓库不再"refs 走了、工作区没走"）` |
| 用户现场 | `git reset --hard HEAD` 后 10 项清空，工作区 == `c7cdd1a` |

## 5. ⚠ 教训：那个 bug 的回归测试，第一版是**假绿**的

第一版夹具写完就通过了 —— 但我按规矩做了**反向验证**（把修复临时短路，强制走旧路径），
测试**依然通过**。也就是说它根本没守住这个 bug。查下去发现夹具缺了两个关键条件：

| 条件 | 第一版 | 为什么必须 |
|---|---|---|
| `core.autocrlf` 在**全局**、本地没有 | ❌ 写进了**本地** | 本地一有，isomorphic 就自己归一化 → 它不再误判，bug 消失 |
| 目标文件的 stat 与 index **不一致** | ❌ `clone` 后 stat 恰好吻合 | isomorphic 的 `compareStats` 在 stat 吻合时**直接信 index 里的 oid**（不读盘、不哈希）；只有 stat 对不上才会读盘重算，这时才轮到"CRLF 字节 vs LF blob"的误判 |

第二版夹具显式制造 stat 失效（**删掉文件再从 index 恢复**，等价于真实仓库里被编辑器/检出写过的 mtime），
并把断言加在"夹具前提"上（`aRow[2] !== aRow[1]` —— isomorphic **必须**把这份工作区误判成已修改）。
两条都满足后，旧路径**如期报红**：

```
FAIL pull：ff 快进必须真的落盘 … -> ff 拉取应成功（旧实现会抛 CheckoutConflictError
并把工作区留在旧版本）: Your local changes to the following files would be overwritten by checkout: a.txt
```

恢复修复代码 → 转绿。这才算真的守住了。

**可复用的结论**：回归测试写完，一定要把修复**短路一次**看它会不会红。
"测过了"和"测得动"是两件事 —— 尤其当 bug 的触发条件依赖环境（全局 vs 本地配置、文件 stat）时，
夹具很容易恰好绕开它。夹具的每个前提条件都该有一条 assert 显式钉住，而不是默认它成立。
