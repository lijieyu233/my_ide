## 2. 六条真实 SQLite 观察（DB-02：C/R，P0）

公共 fixture 为 `items(id INTEGER PRIMARY KEY, name TEXT)`，初始数据 `(1,'one'),(2,'two')`。删除触发器在删除 id=2 时执行 `RAISE(ABORT,'fixture-block')`。以下 IPC 结果均经过原服务 wrap，外层 ok 表示调用是否抛异常，不能混同为事务/落盘成功。

| 编号 | 操作 | 观察结果 | 用户影响与原因 |
|---|---|---|---|
| D1 | `deleteRows(id,'items',['id'],[[1],[2]])` | 返回 `ok:false,error:fixture-block`；磁盘重开仅剩 id=2 | 失败前的 id=1 已持久化；逐条 query 自动导出，没有整批回滚 |
| D2 | 删除不存在的 id=999 | 外层 ok=true，data.affected=1；磁盘仍两行 | affected 使用输入数组长度，成功提示与实际删除数量不一致 |
| D3 | `WITH pick AS (SELECT 2 AS id) UPDATE items SET name='cte-edit' WHERE id IN (SELECT id FROM pick)` | data.ok=select；原连接 id=2 已变，磁盘仍为 two | WITH 开头未被写语句正则识别，修改只留在内存 |
| D4 | `UPDATE items SET name='returning-edit' WHERE id=2 RETURNING id,name` | 返回修改行，但 data.ok=select；磁盘仍为 two | “有结果集”被当作只读，RETURNING 写入不导出 |
| D5 | 依次 `BEGIN`、UPDATE id=2、`ROLLBACK` | UPDATE 返回 write/affected=1；ROLLBACK 报 no transaction is active；内存和磁盘均仍为 two | 事务中的 export 关闭重开数据库，未提交修改被回滚；写入成功响应不能代表修改保留 |
| D6 | `BEGIN; INSERT ... (4,'user-pending')`，随后导入 id=3，再 ROLLBACK | import inserted=1；ROLLBACK 报 no transaction is active；磁盘有 id=3 和 id=4 | 导入吞掉嵌套 BEGIN 错误，随后 COMMIT 同时提交了调用者先前未提交的 id=4 |

D3/D4 的修改可能被后续正常写入一并导出，但本轮没有把这个推断算作第七条复现；已确认的是当次响应后重开文件看不到修改。D5 也不能写成“未提交数据提前落盘”：本轮实际观察是未提交数据被丢弃。

关键代码：`db-service.js:query` 以 `!res.length` 和首词正则决定导出；`deleteRows` 无事务；`importCsv` 的 BEGIN catch 为空。`getRowsModified()` 能提供最近一次完成写操作的数量，不是判断任意 SQL 是否只读的可靠开关。

## 3. 六条启动模块受控观察

使用虚拟配置目录 `C:/audit092`（内存文件系统），监听 PID=999、保存 PID=777、假 spawn PID=555。它们只是测试数值，没有对应真实系统进程。

| 编号 | 注入场景 | 原模块输出/动作 | 证据范围与缺口 |
|---|---|---|---|
| L1 | 无保存状态、无内存 child；netstat 返回端口 18089 的监听者 999 | stopEntry 发出 `taskkill /T /F /PID 999`，返回 ok=true/killed=[999] | 确认仅凭端口选择无归属记录的 PID；未真的杀进程 |
| L2 | 无端口条目保存 PID=777；taskkill 注入 EPERM | 返回 ok=true/killed=[]，状态被删除，同时日志有停止失败 | 停失败仍成功，且失去后续复查记录；LAUNCH-01 C/R |
| L3 | restart：taskkill 失败、netstat 始终返回 999、TCP 探测返回不可连接 | stop 判失败后仍调用一次 spawn，restart 返回 ok=true/pid=555 | 两种探测被刻意注入不同结果，验证忽略 stop 返回值；不代表真实 OS 必定这样探测 |
| L4 | USB start 的 spawnSync 返回 status=7、stderr，error 为空 | 返回 ok=true，保存 pid=0/kind，aliveEntry 返回 alive=true/by=state | 退出码失败被记作成功运行；LAUNCH-02 C/R |
| L5 | USB stop 的 spawnSync 同样 status=7 | 返回 ok=true/killed=0，删除状态 | 未检查退出状态，无法反映桥接停止失败 |
| L6 | 普通条目 start 后设置 keepOnExit=true，再 shutdown | 保留记录中的 command 变成空字符串，cwd 消失 | procs 未存 command/cwd，shutdown 用不完整对象覆盖原身份信息 |

另有 C/H 待验收：start 在 await 端口检查前判断 procs，缺少条目互斥；error 事件只记日志；alive 的 PID 存活或 TCP 连通不证明属于该条目；同步 netstat/USB 调用会阻塞事件循环，但具体 UI 卡顿时长未测。main 的 before-quit 调用异步 shutdown，是否等到清理完成需要真实 Electron fixture，不能凭本轮桩宣称应用退出已可靠。

## 4. 成熟项目与引擎约束

以下官方资料于本轮核查。参考产品的用户行为，实施时仍按 MyIDE 的 Electron/Node/驱动锁定版本验证 API。

| 来源 | 本轮确认 | 转成 MyIDE 合同 |
|---|---|---|
| [DBeaver 自动/手动提交](https://dbeaver.com/docs/dbeaver/Auto-and-Manual-Commit-Modes/) | 区分事务模式，允许提交/回滚并显示事务状态 | 同一连接显示 pending，批量操作不得偷偷提交调用者事务 |
| [sql.js Database API](https://sql.js.org/documentation/Database.html) | export 会关闭重开数据库并重置 PRAGMA；getRowsModified 是最近完成写操作计数；updateHook 存在覆盖限制 | export 必须位于事务边界之后，重开后复位连接配置；不能用 hook/计数单独判读写 |
| [SQLite RETURNING](https://www.sqlite.org/lang_returning.html)、[WITH](https://www.sqlite.org/lang_with.html) | 写语句可返回修改行；WITH 可修饰 SELECT 和写语句 | returnsRows 与 writes 分开，不能靠结果集或首词判断 |
| [SQLite 事务](https://www.sqlite.org/lang_transaction.html) | BEGIN 不能嵌套，嵌套范围应使用 SAVEPOINT | 批次须拥有自己的事务或 savepoint，BEGIN 失败不得继续 COMMIT |

| [VS Code 任务](https://code.visualstudio.com/docs/debugtest/tasks) | 后台任务可以借助输出匹配识别运行状态 | 创建进程、就绪、结束应分别呈现，可选输出条件补充端口条件 |
| [Node child_process](https://nodejs.org/api/child_process.html) | 同步调用阻塞；status、signal、error 含义不同；异步 error/exit/close 有不同事件语义 | 用异步子进程收集实际退出结果，统一终态清理，不能只检查 error |

## 5. 数据库分包实施合同

### DB-A：结果模型与 SQLite 持久化边界（先解决 D3–D5）

影响 `db-service.js`、preload 的结果合同及 `renderer/db-panel.js` 的结果显示。建议分出后端 adapter，服务统一返回：

`{requestId, connectionId, results:[{kind, columns, rows, affected}], transaction:{state, owner}, persistence:{state, errorCode}}`。

- kind 不再用 select/write 二选一承载所有意义；修改可同时返回 rows。多语句执行保留逐条结果，明确哪些语句完成、哪个失败，不能只返回第一结果集。
- 禁止继续扩充首词正则来“修”WITH/RETURNING。先验证当前 WASM/驱动是否提供 statement readonly、autocommit 等能力；sql.js 公开 API不能假定已有这些接口。若需绑定，单独验证版本与资源包兼容；若暂不可得，应限制无法可靠判断的自由 SQL 事务组合并解释原因，不能虚报通用支持。
- 正常自动提交写入后，先完成引擎提交，再导出一次完整字节；用户事务进行中禁止 export。commit/export/file-replace 是不同失败点：已提交但持久化失败时显示 `PERSIST_FAILED`，保留可重试快照/状态，阻止以“保存成功”关闭唯一恢复来源。
- 临时二进制库写完整再替换原文件，失败保留原盘与待恢复内容。与 FS-01 共用文件替换策略，不能走文本编码。导出重开后复位必要 PRAGMA，并重新核对事务状态。
- 连接内串行执行写入/提交/导出/关闭，不能只锁表格按钮而让自由 SQL 插队。不要自动重试可能已执行的非幂等写操作。

验收：D3/D4 结果仍包含正确行，重开文件有修改；D5 在 BEGIN 后改值应保持 pending，ROLLBACK 可执行且磁盘不变，COMMIT 后重开包含改值。另测注释前缀、多个语句、WITH DELETE/INSERT、零匹配 RETURNING、DDL、PRAGMA、导出/替换失败及重新打开后的连接配置。每项验证内存、事务状态、磁盘三者，不能只断言 IPC ok。

### DB-B：批量操作事务所有权与真实 affected（解决 D1/D2/D6）

- 没有用户事务时本批次 begin/commit；已有用户事务时使用本批次唯一 savepoint，成功 release、失败 rollback-to/release，保持外层事务。能力不足时返回 `NESTED_TRANSACTION_UNSUPPORTED`，不吞 BEGIN 失败。
- SQLite 在批次内使用不触发 export 的 adapter 执行，只有最外层提交才进入 DB-A 持久化。外层 pending 时批次成功只表示批次修改留在事务内，不代表已持久化。
- affected 累加后端真实变更数量；不存在主键值为 0，复合主键/重复输入按实际执行结果定义。触发器额外影响与直接 affected 的口径需注明。
- MySQL/PostgreSQL 的 100 行导入批次共用一个连接事务；第二批失败回滚第一批。存储引擎、DDL 隐式提交及驱动取消等能力单独核查，不承诺所有对象可回滚。大 CSV 解析预算/分块后做，不能先扩大吞吐掩盖部分落库。
- 失败结果含阶段、回滚结果和已知事务状态；断线导致提交结果不明返回 unknown，保留诊断而不自动重做整批。

验收：D1 全批失败后重开仍两行；D2 affected=0；D6 导入后外层 ROLLBACK 能同时撤销用户 id=4 与本批 id=3。另外在已有事务内让导入失败，用户之前的修改仍 pending、仅本批撤销。真实三后端测第二批约束失败；服务器未配时标 SKIP，不能用桩宣称真实回滚。

### DB-C：方言先独立交付，取消/结果预算随后

DB-01 仍按 090-F 第一阶段单独修 EXPLAIN；当前只确认 PostgreSQL 代码生成错误，未做真实后端验收。取消/限额另包：requestId 绑定连接与运行语句，后端超时/取消结束真实执行，增量传输限制 rows/bytes；取消后连接可用。UI 截前 1000 行不能作为后端内存预算。先测耗时/峰值再决定 SQLite worker 化，不把主进程 SQL 与 UI 筛选混成同一性能证据。

## 6. 启动分包实施合同

### LAUNCH-A：停止归属和失败保全（L1–L3/L5）

- 每次启动生成 launchId，记录 pid、操作系统创建时间、command、cwd、启动方式、身份核验版本；当前 child 句柄优先，历史 PID 必须重查身份。缺字段的旧记录迁移为 unknown，不能凭一个旧数字 taskkill。
- 端口反查仅是候选集合；不属本条目的监听者返回 `PORT_OWNED_BY_OTHER`。Windows 父子树是否可追踪必须用自有 fixture 验证；Job Object 仅为后续评估项，不先引入未经验证的依赖。
- stop 逐个记录 attempted/confirmedStopped/failed/remainingOwned/foreignListeners；taskkill 成功还需复查退出。无端口也有复查；失败保留身份记录和可重试状态，只在确认停止后清理记录。
- restart 检查 stop.ok；失败返回同一停止诊断，不调用 start。entryId 全链路互斥，在进入第一个 await 前持有操作 token；排队或返回 BUSY，不能双击起两个 shell。
- USB 用异步子进程；spawn error、非零 code、signal、timeout 均失败，日志留有界 stderr。stop 失败保留桥接状态，脚本缺失也不自动宣称已停。

验收先重放 L1–L3/L5 决策；真实 fixture 只操作自己创建的 A/B 子进程：A 结束后 B 占同端口，停止 A 不影响 B；旧 PID 记录身份不符不杀；权限拒绝保留记录；无端口也准确；连续 restart/start/stop 的终态一致。所有后台窗口隐藏，不借用户真实服务取证。

### LAUNCH-B：运行状态、退出与后台保留（L4/L6）

状态提案：`stopped → starting → running → stopping → stopped`，失败进入 failed/unknown 并保留原因；keepOnExit 的 retained 表示退出后保留，不表示就绪。创建 child 不等于 ready；可配置端口/输出条件，但每项绑定同一 launchId，外国监听者不能把条目点亮。

- 子进程 error/exit/close 聚合为一次终态处理，明确资源清理时机；日志和旧事件必须带 launchId，旧进程退出不能删除新进程记录。
- procs 和持久化状态复用完整身份对象，shutdown 不用缺字段结构覆盖它；同时保留真实退出 code/signal 和最后可验证状态。
- 主进程退出前以 guard 协调异步 shutdown，有界等待、避免重复进入 before-quit。停止失败保留诊断；keepOnExit 路径只确认身份与写状态。stopped 统计实际确认数，不用固定 1。
- 轮询支持单次在途与代次，隐藏面板降低频率；异步 netstat/USB 有超时及输出上限。主进程事件循环延迟、面板可操作性需单独测量，不能把同步 API 的存在当作已量化卡顿。

验收：USB status=7 不显示运行；错误启动后可重试；旧 exit 不污染新启动；后台保留再开应用能核对 command/cwd/创建时间；0/1/多个条目的 shutdown 统计准确。真实 Electron headless 验证关闭时停止策略与超时日志，必要截图核对文案，不抢桌面焦点。

## 7. 可直接重放的 SQLite 取证

在仓库根运行下面 Node 代码（可用 PowerShell 单引号 here-string 经 stdin 管道传给 node）。只替换 Electron 模块，不修改 db-service；真实临时目录最后核对路径再删除。基线改变后运行结果可能不同，修复后这些失败应改成正式回归的预期成功行为。

```js
const fs = require('fs'), path = require('path'), os = require('os');
const tempRoot = fs.mkdtempSync(path.join(os.tmpdir(), 'myide-audit092-'));
const handlers = new Map(), m = { exports: {} }, opened = [];
new Function('require', 'module', 'exports', fs.readFileSync('db-service.js', 'utf8'))(
  n => n === 'electron' ? { ipcMain: { handle: (ch, fn) => handlers.set(ch, fn) } } : require(n),
  m, m.exports);
m.exports.registerIpc();
const call = (name, ...args) => handlers.get('db:' + name)({}, ...args);
let SQL;
async function fixture(name) {
  const file = path.join(tempRoot, name + '.sqlite'), db = new SQL.Database();
  db.exec("CREATE TABLE items(id INTEGER PRIMARY KEY, name TEXT); INSERT INTO items VALUES(1,'one'),(2,'two'); CREATE TRIGGER block_two BEFORE DELETE ON items WHEN OLD.id=2 BEGIN SELECT RAISE(ABORT,'fixture-block'); END;");
  fs.writeFileSync(file, Buffer.from(db.export())); db.close();
  const r = await call('connect', { type: 'sqlite', file });
  if (!r.ok) throw Error(r.error);
  opened.push(r.data.id); return { id: r.data.id, file };
}
function diskRows(file) {
  const db = new SQL.Database(fs.readFileSync(file));
  try { return db.exec('SELECT id,name FROM items ORDER BY id')[0].values; }
  finally { db.close(); }
}
(async () => {
  SQL = await require('sql.js')(); const out = [];
  let f = await fixture('partial-delete');
  out.push({ case: 'D1', result: await call('deleteRows', f.id, 'items', ['id'], [[1],[2]]), disk: diskRows(f.file) });
  f = await fixture('affected');
  out.push({ case: 'D2', result: await call('deleteRows', f.id, 'items', ['id'], [[999]]), disk: diskRows(f.file) });
  for (const [name, sql] of [
    ['D3', "WITH pick AS (SELECT 2 AS id) UPDATE items SET name='cte-edit' WHERE id IN (SELECT id FROM pick)"],
    ['D4', "UPDATE items SET name='returning-edit' WHERE id=2 RETURNING id,name"]
  ]) {
    f = await fixture(name);
    out.push({ case: name, result: await call('query', f.id, sql), memory: await call('query', f.id, 'SELECT id,name FROM items ORDER BY id'), disk: diskRows(f.file) });
  }
  f = await fixture('transaction'); await call('query', f.id, 'BEGIN');
  out.push({ case: 'D5', update: await call('query', f.id, "UPDATE items SET name='pending-edit' WHERE id=2"), rollback: await call('query', f.id, 'ROLLBACK'), memory: await call('query', f.id, 'SELECT id,name FROM items ORDER BY id'), disk: diskRows(f.file) });
  f = await fixture('import-owner');
  await call('query', f.id, "BEGIN; INSERT INTO items VALUES(4,'user-pending')");
  const csv = path.join(tempRoot, 'import.csv'); fs.writeFileSync(csv, 'id,name\n3,imported\n', 'utf8');
  out.push({ case: 'D6', importResult: await call('importCsv', f.id, 'items', csv), rollback: await call('query', f.id, 'ROLLBACK'), disk: diskRows(f.file) });
  console.log(JSON.stringify(out, null, 2));
})().catch(e => { console.error(e.stack); process.exitCode = 1; }).finally(async () => {
  for (const id of opened) await call('close', id);
  const abs = path.resolve(tempRoot), base = path.resolve(os.tmpdir()) + path.sep;
  if (!abs.startsWith(base) || !path.basename(abs).startsWith('myide-audit092-')) throw Error('Unsafe cleanup target');
  fs.rmSync(abs, { recursive: true, force: true });
  console.log('TEMP_CLEANED ' + !fs.existsSync(abs));
});
```
