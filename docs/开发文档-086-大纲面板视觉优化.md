# 开发文档-086 · 大纲面板视觉优化 —— 层级颜色分档 + 三角改内联 SVG

> 起因：用户发了一张大纲面板截图（268px 宽、crimson 主题），只有一句「这里的页面不好看」。
> 「不好看」不是可执行的需求，所以这一轮先**量出到底哪里不对**，再动手。
> 结论是两条实打实的缺陷，都不是审美问题。

## 0. 先量再改：实测到的两个缺陷

用真窗口 + 真 IPC 把每行的几何与颜色导出成 JSON（[对照组见 §3]），量表如下：

| 层级 | 实测颜色（crimson） | 字号 | 缩进 |
|---|---|---|---|
| H1 | `rgb(216,179,192)` | 16px | 4px |
| H2 | `rgb(216,179,192)` | 16px | 17px |
| H3 | `rgb(163,121,138)` | 16px | 30px |
| H4 | `rgb(163,121,138)` | 16px | 43px |
| H5 | `rgb(163,121,138)` | 16px | 56px |
| H6 | `rgb(163,121,138)` | 16px | 69px |

**缺陷一：六个层级只压成两档颜色。** H1 与 H2 完全同色、H3~H6 四级完全同色。
一屏看下去「哪层是哪层」只能靠缩进猜。而且 H3+ 的颜色 `rgb(163,121,138)`
**与箭头同色**，三角和文字糊在一起（截图里那串「1. 2. 3.」尤其明显）。

**缺陷二：三角还是字符 `▾`/`▸`。** 而仓库约定（AGENTS.md 第六条）明确：
列表 / 工具条图标一律内联 SVG，理由是 **emoji 与字符的字号、基线不受控**。
文件树（`App.dirIcon`）和启动面板（`launch-caret`）**早就迁到 SVG 了**，只有大纲漏了这一处。
实测 16px 基准下字符三角渲染成 13.6px 字形、撑不满 1.15em 的列宽。

## 1. 修法一：层级颜色分四档（不写死颜色）

原规则只用了两个变量（`--text` / `--text-dim`），所以必然只有两档。
新规则**全部从主题变量混出来**，换主题自动跟随，不需要为每个主题各写一套：

| 层级 | 颜色来源 | 意图 |
|---|---|---|
| H1 | `--text-bright` + `font-weight: 500` | 顶层唯一，一眼定位「这篇在讲什么」 |
| H2 | `--text` | 主层 |
| H3 | `color-mix(--text 62%, --text-dim)` | **过渡档**，避免 H2→H3 掉得太狠 |
| H4 / H5 / H6 | `--text-dim` | 深层级退后（本来就不该抢注意力）|

关键取舍：
- **只降对比、不缩字号** —— 这是文档 054 定下的 PyCharm 约定（各层级字号一致），继续遵守；
  缩进仍是主信号（4 / 17 / 30 / 43 / 56 / 69px 逐级递进），颜色只是补充。
- H1 只加**颜色 + 字重**，不加背景、不加边框 —— 文档 068「同屏强调色预算」的教训是
  一屏多个强焦点等于没有焦点。

## 2. 修法二：三角改内联 SVG

```js
// outline.js —— 与文件树 dirIcon 同一套画法（1.4px 描边、16px 视窗）
const ICO_CHEV = '<svg class="ic" viewBox="0 0 16 16" aria-hidden="true"><path d="M4.6 6.4L8 9.8l3.4-3.4"/></svg>';
```

**没有做两套路径**（展开 / 折叠各一个 SVG），而是**一套路径 + CSS 旋转**：

```css
.ol-arrow svg.ic { width: 1em; height: 1em; transition: transform .12s ease; }
.ol-arrow.closed svg.ic { transform: rotate(-90deg); }
```

理由：`.closed` 这个类早就是折叠态的既有契约（dom 测试与 `--check-ui` 都在断言它），
旋转复用同一个状态，少一条分支、还顺带有了过渡动画。
`.ol-arrow` 也从「靠字体撑宽高」改成明确的 `inline-flex` 居中盒，
这样 svg 有确定的落点，不再受字形基线影响。

⚠ **右键菜单里的 `▸ / ▾` 保留不换** —— AGENTS.md 第六条写明了：
列表 / 工具条的图标用 SVG，但**右键菜单文案惯例带符号前缀**（`✨ 新建文件`），别去"顺手统一"。

### 顺带扩了大纲自检夹具

`scripts/ui-fixtures.js` 的 `_ui_outline.md` 原来只有 H1/H2/H3 三级 —— **验证不出"H3 是独立过渡档"**
（三个层级最多只能体现两档差异）。已扩到 H1~H5 五级（共 6 个标题），`--check-ui` 的 `outlineStructure`
步骤相应从「4 个标题 / 2 箭头 2 占位」更新为「6 个标题 / 4 箭头 2 占位」，并新增两条按**最终 rgb**
比较的断言（真 Chromium 会把 `color-mix` 解析成 rgb）。

⚠ **这里差点留下错数字，值得记一笔。** 改夹具时我凭印象先把期望值写成
「7 个标题 / 3 箭头 4 占位」，**三个数全错**。危险在于：本机 `--check-ui` 跑不起来
（见 §5），这些断言**永远不会被执行**，错数字会一直躺在自检里，等哪天在能跑的环境上
变成一堆假失败、或者更糟 —— 让人以为大纲真的坏了。

发现方式是**另写一个脚本，用与 `check-ui-steps.js` 相同的判定逻辑**去算 fixture 的真实值
（数标题、按 `childrenRange` 的规则数"有子层"的行），再和写死的期望值对照，
当场打出 `标题数 = 6 / 有子层(箭头) = 4 / 叶子(占位) = 2`。
**教训：当一个自检跑不起来时，它的期望值必须用另一条独立路径核对，不能靠肉眼数。**


## 4. 踩坑（这轮新踩的，还是老坑）

**我又用 `Set-Content` 改了一个 `.js`**（想批量替换脚本里的输出文件名），
结果把文件写坏 —— 报 `ReferenceError: fs is not defined`。
AGENTS.md 第三条专门写了这台机器上 PS 的编码链路会写坏源码，**我这轮又踩了第二次**。
正确做法是逐个 `edit`（本轮后半段改回编辑工具，一次就过）。
结论重申：**改任何文本文件都用编辑工具，不用 PowerShell 的 `Set-Content` / `-replace`。**

另一个值得记的：**jsdom 不解析 CSS 变量与 `color-mix()`**，
`getComputedStyle().color` 会原样返回 `var(--text-bright)` / `color-mix(...)` 字符串。
所以 dom 测试里**不能按 rgb 亮度做断言**（第一版写的就是这个，直接失败在 `0 > 0`）。
现在的分工是：
- **dom 测试**：断言"颜色来源不同档"（字符串比较）+ 结构（SVG、字号、缩进、字重）；
- **`--check-ui` / 真窗口**：断言最终 rgb 与亮度关系（只有真 Chromium 才算得出来）。
